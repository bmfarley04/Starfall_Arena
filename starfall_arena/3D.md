# 3D.md

This document governs the active 3D implementation path for Starfall Arena.

Use this doc whenever work is primarily about translating the current duel game from its existing 2.5D / orthographic presentation into a fuller 3D experience.

If you are working on the 3D implemenation, you should ONLY edit scripts in `Assets/Scripts/3d`. Every other gameplay script is part of the 2.5D game. You may read non-3D scripts for reference, but if a 3D task appears to require edits outside `Assets/Scripts/3d`, stop and ask the user for explicit permission before changing any non-3D code. Documentation updates are still required, but if the needed doc change lives outside the 3D docs, ask permission before editing that non-3D doc as part of a 3D-scoped task.

## Purpose

The goal is not to replace the game's core identity.

The goal is to preserve almost all current duel systems while changing how the game is spatially presented, moved, read, and eventually played in 3D.

That means the 3D effort should generally preserve:

- the duel-first game structure
- the two-player combat focus
- existing ship classes, weapons, abilities, augments, HUD expectations, and round flow unless a change is intentionally required
- controller-first usability
- keyboard-and-mouse support
- the active networking direction
- performance targets appropriate for a PS4 build

The default assumption should be:

- keep the gameplay rules unless 3D implementation makes a rule impossible or clearly harmful
- change presentation, movement interpretation, camera behavior, targeting context, and supporting systems only where needed
- engineer 3D systems in a way that stays compatible with the existing networking direction documented in `NETWORK.md`, instead of creating local-only behavior that will be expensive to retrofit for server-authoritative play later
- engineer 3D systems with performance in mind from the start, especially for PS4-class hardware, instead of assuming expensive effects or allocation-heavy workflows can be cleaned up later

## Relationship To Existing Docs

`GAME_SYSTEMS.md`, `UI_MANAGERS.md`, and `NETWORK.md` still describe the current live game.

`3D.md` exists to document how the 3D implementation should adapt or reinterpret those systems.

When working on 3D features:

- read `3D.md` first
- then read `GAME_SYSTEMS.md` for the underlying gameplay system being preserved
- read `UI_MANAGERS.md` if the 3D work affects HUD, menus, selection flow, or scene flow
- read `NETWORK.md` if the 3D work affects network authority, prediction, sync strategy, or remote presentation
- keep implementation edits inside `Assets/Scripts/3d` unless the user explicitly approves broader changes after the need is identified

If a 3D change directly alters one of those shared systems, update both this file and the affected subsystem doc.

## Current 3D Direction

The current 3D effort should be treated as an implementation track for the same game, not as a separate game mode.

The intended direction is:

- move from orthographic 2.5D presentation toward a perspective-driven 3D experience
- preserve combat readability and fast duel clarity
- preserve current game logic where possible
- replace only the assumptions that are specifically tied to the 2D plane

Current likely focus areas include:

- 3D ship movement and steering
- camera framing and perspective readability
- translating thrust, banking, pitch, and visual feedback into 3D
- adapting aiming, target readability, projectile readability, and combat spacing
- determining which existing 2D physics assumptions can remain and which need true 3D replacements

## Current 3D Architecture

The 3D ship path now uses the same identity split as the 2D game, but the real behavior is distributed across focused components instead of being concentrated in one movement script.

```text
Entity3D
  -> Player3D
  -> Enemy3D
```

These classes should stay narrow and mainly coordinate dedicated 3D systems.

Current shared 3D ship systems:

- `ShipFlight3D`
  - shared rigidbody flight
  - assisted pitch/yaw steering driven by filtered input and acceleration-limited turn rates
  - full 3D forward thrust, local drift damping, velocity alignment assist, and max-speed clamping
  - optional world-Y plane lock remains only as a fallback/debug path, not the active player-flight default
  - reusable by local player, AI, or future network drivers
- `ShipVisualTilt3D`
  - banking and pitch lean on the ship visual model
  - reads steering intent plus flight telemetry so the mesh leads turns instead of only reacting after rigidbody motion
- `ShipThrusterVfx3D`
  - thrust-driven thruster playback and intensity
- `ShipSpeedFx3D`
  - shared speed-based VFX such as dust/trails
  - can now auto-build layered `TrailRenderer` ribbons from authored wing source transforms so 3D ships can keep speed streak setup inspector-driven instead of hand-authoring multiple trail components per prefab
- `DeathEffects3D`
  - shared ship death explosion/audio trigger and ship-part scatter kickoff
- `ShipPartScatter3D`
  - detached 3D ship-fragment tumble, drift, shrink, and cleanup runtime
- `SplitStateLightningRig3D`
  - shared split-state lightning coordinator for grouped anchored bolts on a 3D ship
  - toggles child `LightningBolt3D` renderers together and pushes a shared intensity multiplier through material property blocks
- `TimedEffectCleanup3D`
  - auto lifetime cleanup for one-shot 3D VFX, with destroy vs pool-despawn handling
- `ShipSplitOffsetRig3D`
  - shared split-state offset coordinator for grouped ship pieces
  - caches each piece's authored local position and applies inspector-configured additive local offsets while the split state is active
- `ProjectileWeapon3D`
  - shared projectile spawn/cooldown ownership for both player and enemy ships
  - owns inspector-configured projectile fire audio for the 3D path
  - base projectile fire now also spends an overheat-style energy cost against the owning `Entity3D`
- `StupidTurret3D`
  - scene-test firing driver for stationary or non-piloted 3D ships
  - continuously calls the ship's basic `ProjectileWeapon3D` without producing movement input
  - should be paired with `ProjectileWeapon3D` aim set to `MuzzleForward` when the goal is "fire where the ship is facing"

Current player-only 3D systems:

- `PlayerInput3D`
  - local input adapter
  - feeds movement and weapon systems instead of movement reading raw input directly
  - when the active `PlayerInput` control scheme is `key+mouse`, free-look is sourced from locked mouse delta instead of an unlocked pointer position so KBM camera rotation can continue indefinitely like a standard shooter/space-flight control scheme
- `PlayerCameraRig3D`
  - Cinemachine follow-offset, damping, and FOV behavior
  - intentionally allows turn-driven off-center framing so hard maneuvers can push the ship across the screen before the camera recenters
  - only belongs on the local player path
- `Player3D`
  - owns local-player-only 3D coordination, victim-side hit audio, and the dedicated `OnAnchor` input state
  - Anchor is a hold input that suppresses thrust while applying a configurable rotation multiplier for fast facing changes
  - while Anchor is active, `Player3D` also drives optional split-state presentation rigs such as lightning bolts and grouped ship-piece offsets
- `PlayerHUDManager3D`
  - shared local-player binding source for scene HUD objects in the 3D path
  - resolves the correct player once and broadcasts that binding to dedicated HUD element scripts instead of letting each player prefab push itself into shared UI
  - currently resolves the local player from the active local input path; this should move to NGO ownership once the 3D network player path exists
- `PlayerHealthShieldHUD3D`
  - scene HUD health/shield presenter for the local player
  - subscribes directly to `Player3D.HealthChanged` and `Player3D.ShieldChanged`
- `PlayerWeaponSelectionHUD3D`
  - selected-weapon outline/select-bar presenter for the local player
  - weapon select bars now support per-slot fill behavior so a slot can display either remaining resource availability or cooldown ready progress
  - cooldown-driven slots can use a dedicated recharge color, briefly flash white when they become ready, then settle to a configurable ready color
  - intended to live on the spawned weapon/ability HUD prefab rather than on the binding source itself
- `PlayerAbilitySelectionHUD3D`
  - cooldown-only ability outline/select-bar presenter for the local player
  - acts purely as a cooldown monitor rather than a selected-slot presenter
  - each slot drives cooldown ready progress on the fill bar and swaps the surrounding box between base vs ready visuals
  - ready transitions flash the surrounding box white with configurable duration/alpha instead of flashing the fill bar
  - intended to live on the spawned weapon/ability HUD prefab rather than on the binding source itself
- `PlayerWeaponAbilityHUDSpawner3D`
  - spawns the local player's weapon/ability HUD prefab under the scene HUD once a player binding exists
- `PlayerAimReticle3D`
  - local-player HUD reticle controller for center-screen aiming readability
  - now binds through `PlayerHUDManager3D` so it can live on a scene HUD canvas instead of assuming it is attached to the player root
  - smoothly closes the outer brackets when the same center-screen aim ray lands on an enemy
  - uses a forgiving center-screen spherecast for enemy hover/readability detection
  - spins the inner reticle while the primary projectile weapon is actively firing or has just fired
  - can tint inspector-assigned dash-mark images and the inner-circle image while the reticle is in its firing pulse, with separate idle/firing colors plus serialized idle/firing alpha
  - can fill optional left/right bracket images from the owning `Entity3D` primary-weapon overheat ratio instead of using a separate HUD-only timer
  - supports additional ability-driven spin sources so beam-style hold weapons can spin continuously while active and charged-shot abilities can pulse spin only when the shot actually releases
  - should read the same camera/aim source as `ProjectileWeapon3D` so HUD feedback matches real projectile direction
- `GigablastChargeEdgeGlow3D`
  - local-player fullscreen Gigablast edge-glow controller
  - reads `GigaBlast3D` charge progress and drives shader globals for the 3D charge-screen effect
  - must stay owned by the local player camera path rather than shared ship runtime
- `PlayerChromaticAberration3D`
  - local-player chromatic-aberration hit feedback controller for the 3D path
  - reads real damage applied by `Player3D.TakeDamage(...)` and drives a URP `ChromaticAberration` override on the assigned gameplay `Volume`
  - supports optional non-damage impulses through a public API so teleport, special fire, or future local-only feedback can add the same screen treatment without duplicating fade logic
  - should stay on the local player camera path and should prefer an explicit `Volume` reference over blind scene search when multiple volumes exist
- `GigablastEdgeGlowRendererFeature`
  - URP fullscreen render pass for the 3D charge-screen effect
  - samples camera color, computes nearest-screen-edge glow, and adds HDR border color before post-processing so bloom can catch it

Current enemy-only 3D systems:

- `EnemyAIFlightController3D`
  - produces the same movement-intent shape as player input so enemies can reuse `ShipFlight3D`

`Assets/Scripts/3d/Movement3D.cs` now exists as a compatibility coordinator for older prefabs/scenes that were already wired against the previous monolithic script. New 3D work should prefer the componentized scripts directly.

Current 3D projectile split:

- `ProjectileWeapon3D`
  - owns fire cadence, muzzle selection, aim resolution, projectile spawn, and muzzle FX
  - owns the shared `SoundEffect` hook for 3D projectile fire
- `Projectile3D`
  - owns projectile travel, hit detection, hit results, hit FX, and despawn/pool return

For player-facing readability, projectile fire direction should be resolved from the intended aim target, not from a muzzle transform that may be attached under a visually banked or pitched ship mesh.

Current implementation rule for 3D projectile visuals:

- 3D projectile prefabs should stay lightweight visual/data carriers
- if projectile hit detection is already handled by scripted raycasts or sweep tests, do not also add projectile colliders or rigidbodies
- only keep collision components on the real world targets that need to be hittable

This matters for the 3D duel path because projectile counts and VFX density can grow quickly, and redundant per-projectile physics components add cost without improving hit authority when the game is already using explicit hitscan-style evaluation.

## Implementation Principles

When building the 3D version:

- preserve existing gameplay behavior first, then expand
- avoid rewriting stable combat systems just because the presentation changed
- prefer adaptation layers over full-system replacement when possible
- keep inspector-driven tuning for movement, camera, feedback, and combat readability
- preserve controller-first input feel
- do not silently break networking assumptions while experimenting with 3D movement or camera work
- treat networkability as a first-class engineering constraint for 3D work, especially for movement, aiming, combat timing, camera-driven assist logic, and stateful VFX that may need remote presentation
- treat performance as a first-class engineering constraint for 3D work, especially for VFX counts, spawned objects, update-loop cost, memory churn, and expensive camera or physics helpers

3D implementation should stay performant for a PS4-targeted build:

- prefer object pooling over repeated instantiate/destroy loops for gameplay objects and effects
- avoid unnecessary per-frame allocations, transient garbage, or hidden editor-friendly patterns that scale poorly in play
- be careful with particle counts, post-processing, camera effects, and repeated physics queries
- design shared systems so they can scale to real match conditions rather than only working in isolated test scenes
- call out early when a visually attractive 3D feature has a likely platform-cost problem
- for ship split-state lightning, prefer anchored bolt meshes driven by explicit start/end transforms instead of spraying many free-floating particles around the hull; the shader defines the look, but the mesh and anchors define where the effect exists in world space

3D implementation should stay easy to network in accordance with `NETWORK.md`:

- favor deterministic or clearly authoritative gameplay state over presentation-driven hidden state
- keep ownership and authority boundaries clear
- avoid coupling core gameplay results to local camera-only calculations when those results will need to match across clients
- prefer data that can be replicated, predicted, reconciled, or reconstructed cleanly instead of ad hoc local-only behavior
- call out early when a 3D feature probably needs explicit support in the network layer rather than assuming it can be bolted on later

The current component split supports that direction:

- flight intent can come from player input, AI, or future networking drivers without changing the flight system
- camera behavior is isolated from shared ship movement so non-local ships do not inherit hidden local-only state
- projectile firing is owned by a reusable weapon component instead of duplicated across ship types

## 3D Script Folder Layout

`Assets/Scripts/3d` should stay organized by subsystem responsibility instead of collecting every 3D script in one flat folder.

Current folder contract:

- `Core`
  - shared 3D base types and config/data definitions
  - examples: `Entity3D`, `Ship3DTypes`
- `Entities/Player`
  - player-only 3D entity coordination, input, and local camera ownership
  - examples: `Player3D`, `PlayerInput3D`, `PlayerCameraRig3D`, `PlayerHUDManager3D`
- `UI`
  - local-player 3D HUD widgets and HUD-binding targets
  - examples: `PlayerAimReticle3D`, `PlayerHealthShieldHUD3D`, `PlayerWeaponSelectionHUD3D`, `PlayerWeaponAbilityHUDSpawner3D`
- `Entities/Enemy`
  - enemy-only 3D entity coordination and AI flight intent
  - examples: `Enemy3D`, `EnemyAIFlightController3D`
- `Flight`
  - shared 3D ship movement and reusable flight behavior
  - examples: `ShipFlight3D`
- `Combat`
  - projectile firing, projectile behavior, and other 3D combat-runtime scripts
  - examples: `ProjectileWeapon3D`, `Projectile3D`, `PhysicalProjectile3D`, `Ability3D`, `Beam3D`, `LaserBeam3D`
- `Effects`
  - shared ship presentation and combat/VFX support scripts
  - examples: `ShipVisualTilt3D`, `ShipThrusterVfx3D`, `ShipSpeedFx3D`, `DeathEffects3D`, `ShipPartScatter3D`, `TimedEffectCleanup3D`
- `Effects/ShaderControllers`
  - shader-driven 3D effect controllers
  - examples: `LightningBolt3D`, `SplitStateLightningRig3D`
- `Pooling`
  - shared 3D object-pool helpers
  - examples: `GameObjectPool3D`, `PooledObject3D`
- `Legacy`
  - temporary compatibility shims kept only to avoid breaking older prefabs/scenes during the 3D transition
  - examples: `Movement3D`

When adding a new 3D script, place it under the subsystem it serves first. Do not add new scripts back into the root `Assets/Scripts/3d` folder unless the folder structure is being intentionally redesigned and this doc is updated with that change.

Current split-state lightning authoring rule:

- put the lightning look in `Assets/Shaders/LightningBolt3D.shader` and a shared material asset such as `Assets/Materials/3d/ShipSplitLightningBolt.mat`
- place one child `LightningBolt3D` object per visible hull seam or ship split, with explicit start/end anchor transforms on the ship prefab
- use `SplitStateLightningRig3D` on the ship root or effect root when multiple bolts should enable/disable together for the split-state presentation
- keep split-state activation outside the shader; the shader stays visual-only while the rig or gameplay presenter decides when bolts are active

3D work should explicitly call out when it is:

- purely visual
- a control-feel change
- a camera/readability change
- a real gameplay-rule change
- a networking-impacting change

## 3D Ability System

The 3D ability system mirrors the 2.5D pattern: `Entity3D` holds an array of 4 optional `Ability3D` slots, each a MonoBehaviour component on the same GameObject. `PlayerInput3D` routes `OnAbility1`–`OnAbility4` input callbacks to the corresponding slot.

Core architecture:

- `Ability3D` — base class in `Combat/`. Provides `TryUseAbility(InputValue)` input routing, optional cooldown/duration query hooks, lock/disable flags, rotation/thrust multipliers, HUD state hooks, and helpers to check/disable sibling abilities.
- `Ability3D` input rule — the base class is responsible for press-vs-release routing. Hold/release abilities should use base hooks such as release handling and optional timestamp gating instead of replacing the entire input path unless there is a concrete reason the base contract is still insufficient.
- `Entity3D` — owns `Ability3D[] abilities` (size 4), assigned in Inspector. Calls `Die()` on each ability during entity death.
- `PlayerInput3D` — routes ability input to `Entity3D.GetAbility(index)?.TryUseAbility(value)`.

Current ability implementations:

- `Beam3D` — hold-to-fire continuous beam (Class1 Ability 1). Uses capacity system (drain while firing, regen while idle). Spawns a `LaserBeam3D` prefab as a child of the entity and owns the looping beam-fire `SoundEffect`.
- `LaserBeam3D` — beam weapon runtime. Drives a LineRenderer + optional impact/muzzle particle transforms from F3D asset pack visuals. Uses camera-center aiming (same pattern as `ProjectileWeapon3D`). Applies continuous DPS via `Entity3D.TakeDamage()`, triggers shield hit effects at intervals. No dependency on F3D scripts.
- `Reflector3D` — Class1 reflect ability for the 3D path. Owns cooldown, active window, projectile reflection rules, and the reflected-projectile `SoundEffect`.
- `ReflectShield3D` — shield-mesh runtime used by `Reflector3D`. Preserves the 2.5D shield fade/ripple shader behavior and applies the reflected projectile state after the ability approves the hit.
- `Teleport3D` — blink movement ability for the 3D path. It exposes separate origin and destination pulsewave configs so teleport departure and arrival can use different Forge pulsewave prefabs and can independently play as expanding or collapsing waves without editing the third-party asset script.
- `Player3D` — owns local-player-only 3D coordination plus victim-side hit audio, including shield/hull impact sounds and the looping beam-hit `SoundEffect`.

- `EmpoweredShot3D` â€” Class2 empowered projectile ability for the 3D path. Reuses `ProjectileWeapon3D` aim and muzzle handling, overrides projectile combat values, and carries its slow debuff through the 3D projectile/entity runtime.
- `Class2Shield3D` â€” Class2 temporary absorb shield for the 3D path. Uses the existing shield-mesh visual runtime for activation and hit ripples, but consumes incoming explicit-sweep projectiles instead of reflecting them.
- `TractorBeam3D` â€” Class2 cone pull ability for the 3D path. Builds a lightweight runtime cone mesh, plays optional suction VFX/audio, and pulls overlapping `Rigidbody` targets toward the ship inside a planar forward cone.
- `PhysicalProjectileAbility3D` â€” Class2 shield-bypassing projectile ability for the 3D path. Fires a `PhysicalProjectile3D` through `ProjectileWeapon3D` so the shot keeps the shared 3D spawn, aim, and recoil rules while still dealing direct hull damage.

Current player control rule:

- `Anchor` is a dedicated 3D player hold input handled by `Player3D`, not one of the four `Ability3D` slots
- while held, Anchor applies `Player3D` inspector-configured thrust and rotation multipliers to `ShipFlight3D`
- while held, Anchor also enables any configured `SplitStateLightningRig3D` and `ShipSplitOffsetRig3D` components under the player
- default 3D Anchor tuning is `thrustMultiplier = 0` and `rotationMultiplier = 3`

Current 3D flight rule:

- the active 3D player flight path now uses true climb/dive movement; forward thrust follows the ship's real facing direction in world space
- assisted steering is the default control law for the 3D path; input defines a desired turn state and `ShipFlight3D` accelerates into and out of that turn instead of writing raw angular velocity directly from input
- cinematic readability for the 3D player path depends on `ShipFlight3D`, `ShipVisualTilt3D`, and `PlayerCameraRig3D` being tuned together; the ship is intentionally allowed to ride off-center during hard turns instead of being instantly recentered every frame

Beam aim direction rule: `LaserBeam3D` resolves aim from camera center (`Camera.ViewportPointToRay(0.5, 0.5)`), not from `transform.forward`. This matches the projectile weapon rule — visual banking/pitching can rotate the beam's parent transform away from where the player is actually aiming.

- `GigaBlast3D` â€” Class1 charged projectile ability for the 3D path. Holds to charge through four tiers, applies tier-based thrust/rotation penalties while charging, and fires tier-specific projectile prefabs through `ProjectileWeapon3D` so the shot reuses the 3D muzzle and camera-aim rules.
- `GigaBlastProjectile3D` â€” optional projectile runtime for GigaBlast tiers that need piercing. It preserves the normal `Projectile3D` hit path, but lets high-tier shots continue through multiple valid ship targets while reducing damage after each hit.

## Documentation Rules For 3D Work

When a change is specific to the 3D implementation path, document it here.

When a change modifies shared game behavior, also document it in the shared gameplay/UI/network doc that owns that behavior.

When a 3D change creates new networking constraints, prediction requirements, replication needs, or authority questions, also update `NETWORK.md`.

Bug notes for 3D implementation should be written here when the issue is mainly caused by the 3D translation layer.

Keep 3D bug notes short and actionable:

- what failed
- why it matters in the 3D path
- how to avoid repeating it

Bug note:

- shared 3D victim-hit audio cannot infer beam-vs-projectile behavior after the fact if `Entity3D.TakeDamage(...)` drops the damage source. The earlier contract only passed damage, hit point, and attacker, which meant `Player3D` had no reliable way to decide between shield/hull impact sounds and the looping beam-hit sound. Keep the 3D damage path explicit about source type whenever downstream feedback depends on it.
- shared 3D movement scripts must not own local-player camera logic. The earlier `Movement3D` mixed universal flight with Cinemachine behavior, which made enemy or future network-driven ships inherit irrelevant camera dependencies. Keep flight reusable and keep camera behavior on player-only components.
- shared 3D projectiles must not trust a tilted visual muzzle's forward vector for player aiming. Once banking/pitching is applied to the visual model, muzzle children can tilt away from the real gameplay aim. Resolve player projectile direction from camera aim or another authoritative target point, then spawn from the muzzle position using that direction.
- shared 3D center-screen projectiles must not rely on muzzle-to-center-point convergence alone once the camera is allowed to lag and frame the ship off-center. That path is mathematically valid but can look like shots are missing the reticle during hard turns because the muzzle starts far from the center ray. Keep a tunable blend back toward the raw center-screen aim direction so off-center chase framing still reads as center aiming.
- shared 3D projectiles must not carry redundant physics components when the hit path is already explicit hitscan/sweep logic. The earlier 3D projectile version kept a projectile collider even though collision results were being decided by scripted casts. That added avoidable component cost and blurred the true ownership of hit detection. Keep the projectile prefab visual-only unless a real gameplay requirement needs its own physics body.
- shared 3D flight must not let pitched root rotation leak into a duel-plane movement basis. An earlier `ShipFlight3D` version used the ship's full `transform.forward` for thrust, recoil, and speed evaluation, so rotating the ship off the horizontal plane silently injected world `Y` velocity and looked like gravity was turning on during turns. Keep duel-plane movement projected onto a stable world plane and explicitly zero vertical drift when this path is meant to stay planar.
- shared 3D flight must not keep planar-forward thrust enabled on the active player flight path after the design has moved to real climb/dive. The old `ShipFlight3D` projected thrust and recoil onto a world-horizontal basis and then zeroed `velocity.y`, which made pitch visuals look responsive while actual travel stayed trapped on the old duel plane. If the 3D mode is meant to support real ascent and descent, thrust/recoil must use full forward and the world-Y lock must stay off on the active prefab.
- shared 3D turn feel must not rely on post-physics reactions alone. The earlier combination of direct angular-velocity assignment, reactive-only mesh banking, and a camera that only changed FOV/distance made the ship feel late and disconnected even when the model visibly tilted. Keep steering assist, intent-driven visual tilt, and turn-biased camera framing coordinated as one package.
- shared 3D entities must own shield state and the `ShieldController` reference directly, just like the 2.5D `Entity` path. The earlier `Entity3D` only tracked hull health, so 3D projectiles skipped shield absorption entirely and never triggered the canonical field flicker on hit. Keep shield consumption and shield-hit visual triggering inside `Entity3D.TakeDamage(...)` so every 3D ship reuses the same hook-up pattern.
- shared 3D projectiles must resolve the owning `Entity3D` from the hit collider's rigidbody or parent chain before deciding whether damage should apply. In the 3D scene, shots can hit child colliders such as shield meshes or visual model colliders that are intentionally untagged. If `Projectile3D` only checks the exact hit collider for both tag matching and `Entity3D`, the projectile despawns without ever calling `TakeDamage(...)`.
- shared 3D temporary shield abilities must intercept projectiles from the explicit `Projectile3D` hit path rather than relying on passive trigger callbacks from the shield mesh. A Class2 absorb shield can look visually correct as soon as its shield object is active, but explicit spherecast hits still flow into normal damage unless `Projectile3D.ProcessHit(...)` delegates that impact to the ability first. Keep projectile-impact overrides explicit in the 3D projectile runtime whenever an ability is supposed to absorb, redirect, or otherwise replace the default hit result.
- shared 3D hold abilities such as `Beam3D` must not inherit tap-ability cooldown gating from `Ability3D.TryUseAbility(...)`. That base path timestamps the press event, which is fine for tap abilities but wrong for hold/release weapons and can look like the beam randomly expires or has a fake regen delay before it can fire again.
- shared 3D beam capacity is an overheat meter, not remaining fuel. If `drainRate <= 0` or `capacity <= 0`, the 3D beam should be treated as non-draining and the HUD/resource gate should stay inactive instead of accumulating invisible heat.
- shared 3D reflect shields cannot rely on `OnTriggerEnter`-style callbacks from the projectile itself when the projectile path is explicit sweep logic. `Projectile3D` decides hits by spherecasting and may not carry a live collision body, so the reflect path has to be checked from `Projectile3D.ProcessHit(...)` before normal damage/despawn logic runs.
- shared 3D reflect shields must not treat reflection as a simple `-direction` flip when the gameplay goal is "send the shot back to who fired it." In full 3D space the attacker can sit above, below, or offset from the incoming path, so a planar reversal can miss even though the parry looked correct. Resolve the reflected heading from the projectile position to the original shooter when that shooter still exists, and only fall back to a raw reverse vector if that ownership context is gone.
- shared teleport abilities reused from the 2D path must not keep `transform.up` movement, `z` pinning, or `Collider2D`-only disable/restore logic once they are placed on 3D ships. That combination makes the ship blink but still teleport in the old 2D axis basis, leaves 3D colliders active during the warp, and can restore the wrong post-teleport scale if the mesh prefab is authored with non-unit local scale. Resolve teleport travel from the ship's planar 3D forward, preserve the 3D flight-plane axis, and cache/restore both 2D and 3D presentation state.
- shared 3D teleport pulsewave VFX must not keep a fixed world rotation when the gameplay camera follows ship heading. A flat pulse mesh that spawns with a static rotation can look correct from one heading and edge-on or skewed from another. Billboard teleport pulsewaves to the active gameplay camera, and preserve any mesh-authoring axis offset the prefab needs, so departure and arrival reads stay consistent regardless of ship facing.
- shared 3D teleport one-shot audio must not reuse a player-level `AudioSource` that may already be configured for looping beam, shield, or other sustained effects. `SoundEffect.Play(...)` uses the source's current loop state, so a reused looping source makes teleport exit/arrival sounds loop even though the ability only triggers them once. Keep teleport on its own dedicated non-looping `AudioSource` so one-shot playback cannot inherit stale loop settings from another 3D system.
- shared 3D ability hooks must be consumed by the movement and firing drivers, not just exposed on `Ability3D`. Before `GigaBlast3D`, the 3D runtime defined thrust multipliers, rotation multipliers, and primary-fire locks, but `ShipFlight3D`, `PlayerInput3D`, and the enemy fire loop never read them. That made charge penalties and fire suppression look configured in the ability while doing nothing in play. Keep the runtime querying `Entity3D` for combined ability state whenever a new 3D ability relies on those hooks.
- shared 3D debuff projectiles must extend both `Projectile3D` and `Entity3D` when ported from the 2.5D path. A first-pass Class2 empowered shot port can fire the right projectile prefab and still silently drop its slow effect if the 3D path only ports the ability and not the target-side movement scaling. When a 2.5D projectile carries gameplay state such as slow, burn, or pierce decay, audit both the projectile runtime and the target entity runtime before assuming the ability port is complete.
- shared 3D charged projectiles must not assume every tier prefab shares the same pivot length. `GigaBlast3D` can swap between very short and very long projectile meshes, and some of those prefabs use a midpoint pivot. If every tier uses the same spawn distance, long shots can spawn back through the ship even though short ones look correct. Keep per-tier forward spawn compensation exposed in the ability config when the projectile art varies by tier.
- shared 3D visual tilt must not derive recoil pitch only from total forward acceleration. In the 3D flight path, weapon recoil is injected as a velocity impulse, so folding it into the same signed acceleration term as thrust can invert the feel and removes any independent tuning. Keep thrust pitch and recoil pitch as separate inputs, with recoil sensitivity exposed on `Entity3D`.
- shared 3D death presentation must not stay embedded in `Entity3D` or reuse the 2D ship-part scatter script unchanged. The old path depended on `Rigidbody2D`, planar cone math, and a fake `z` render offset, which makes detached debris read wrong once the ship is a true 3D object. Keep ship death VFX in `DeathEffects3D`, keep per-fragment behavior in `ShipPartScatter3D`, and scatter with real 3D velocity and angular motion.
- shared 3D one-shot particle effects must not rely on scene unload or manual cleanup to disappear. That leaves invisible-but-alive objects in the scene and defeats pooling. Use `TimedEffectCleanup3D` so temporary VFX either despawn back into `GameObjectPool3D` or destroy themselves after their particle lifetime expires.
- shared 3D split-state lightning must not treat the shader asset itself as if it can place lightning in the world. The earlier confusion came from stopping at the shader/material step, which produced no controlled ship effect because nothing was defining where the pixels should render. For ship seam lightning, always attach the material to a mesh-bearing `LightningBolt3D` object with explicit anchor transforms, and group those bolts under `SplitStateLightningRig3D` when the whole split-state effect should toggle together.
- shared 3D split-state lightning must not blindly reset bolt visibility in `Awake()` without respecting the renderer's authored enabled state. An earlier `LightningBolt3D` version defaulted its private visibility flag to `false` and then applied that to the `MeshRenderer` on play start, which made bolts look correct in edit mode but disappear the moment the scene began. Cache the renderer's authored enabled state before applying runtime control so preview-visible bolts remain visible unless a rig or gameplay script intentionally hides them.
- shared 3D split-state lightning must not assume every discovered `LightningBolt3D` is fully configured when a rig toggles the effect on startup. An earlier version let `SplitStateLightningRig3D` enable bolts immediately, and any bolt missing a `startPoint` or `endPoint` crashed inside `UpdateQuad()`. Guard bolt activation against missing anchors, log the setup error once, and fail closed by hiding the invalid bolt instead of throwing.
- local-player 3D charge-screen effects must not be implemented as a center-distance vignette when the desired read is energized screen edges. The vignette path biases the effect toward radial darkening/tinting and visibly contaminates the center of the frame. For Gigablast, compute glow from nearest-screen-edge distance in a fullscreen pass and add it over the scene color instead.
- local-player 3D fullscreen charge effects must stay owned by one local camera path only. If multiple controllers write the same global edge-glow parameters, whichever updates last wins and the wrong camera can inherit another ship's charge state.
- local-player 3D anchor states must suppress the effective thrust signal, not just the acceleration application. If Anchor only blocks velocity gain while `ShipFlight3D` still reports raw thrust input as active, thruster VFX and any other thrust-driven presentation keep firing and falsely imply the ship is accelerating.
- shared 3D split-state piece offsets must be applied as `authored local position + configured offset`, not as an overwrite of the current transform or as repeated incremental pushes. Otherwise the effect either destroys prefab-authored asymmetry or accumulates drift every time the split state toggles.
- local-player 3D KBM free-look must not depend on an unlocked mouse cursor or on stick-style action values alone. In the 3D duel camera path, that caps rotation when the pointer hits the screen edge and can leave the mouse acting like a UI cursor instead of a relative-look device. Keep KBM free-look reading locked mouse delta through `PlayerInput3D`, and only apply that cursor lock while the active control scheme is `key+mouse`.
- local-player 3D aim-reticle feedback must not raycast from a different origin or camera than the actual weapon aim path. If the HUD closes brackets from `transform.forward` or a different camera while `ProjectileWeapon3D` fires from screen-center camera aim, the reticle can claim "enemy under aim" even though the real shot line disagrees, or stay open while shots are correctly centered. Keep hover/readability checks sourced from the same center-screen aim ray the weapon uses.
- local-player 3D reticle spin must not assume "ability button is being held" means "a shot just happened." Charged abilities such as `GigaBlast3D` can spend most of their lifetime in a held charge state where the player is not actually firing yet, while beam-style abilities really do need continuous spin the whole time they are active. Keep reticle spin sourced from actual weapon fire timestamps or explicit ability spin providers instead of raw input state alone.
- shared 3D primary-weapon overheat must not be tracked separately by the weapon gate and the HUD reticle. If `ProjectileWeapon3D` enforces one heat value while `PlayerAimReticle3D` animates a different local approximation, the player gets false feedback about why base fire stopped and future tuning becomes misleading. Keep the overheat state authoritative on `Entity3D`, spend it from the real base-weapon fire path, and have the reticle read that same normalized value for bracket fill.
- shared 3D beam visuals must not use `SphereCast` entry distance as the rendered beam length when the hit effect is placed at `hit.point`. With a forgiving beam radius, `RaycastHit.distance` reports when the cast sphere first touches the target, which makes the visible beam stop short by roughly the cast radius even though damage and impact VFX land correctly. When the beam should visually reach the displayed impact point, derive the rendered length from the hit point projected onto the beam direction instead of the raw cast-entry distance.
- local-player 3D chromatic-aberration hit feedback must not reuse the 2.5D path's `impactForce`-driven intensity calculation without rechecking the 3D damage contract. The old player script scaled the effect from impact force instead of real damage taken, but the 3D projectile and beam paths currently call `TakeDamage(...)` without any separate impact-force payload. A direct port therefore looks "wired" in code while producing little or no visible response in play. In the 3D path, drive chromatic intensity from the actual shield/hull damage applied and keep the post-process controller local to the player camera runtime.
- shared 3D speed trails must not be authored from the ship root or from a single center emitter when the look goal is wingtip streaking. That setup turns the effect into a flat center ribbon and breaks the silhouette read from behind. Author explicit wing source transforms and let `ShipSpeedFx3D` build the layered trail renderers from those points so the streaks stay attached to the ship's lateral silhouette.
- shared 3D speed trails must not offset the emitter itself away from the authored wing transform just to fake camera-facing softness or turbulence. World-space emitter drift makes the trail read like it is detached from the hull during flight. Keep the emitter locked to the wing source and let the trail renderer alignment, material, width curve, and gradient sell the softness instead.
- local-player 3D health/shield HUD ports must not move the 2.5D combat-state update logic into a scene manager just because the canvas is different. In the 2.5D path, `Player` owns HUD initialization plus `OnHealthChanged()` / `OnShieldChanged()` updates, while the scene manager only supplies the correct canvas binding. Rebuilding the bars from scene-level polling or phase flow makes the HUD easier to desync from real combat state. Keep the 3D HUD as a thin local-player binder that `Player3D` updates directly from combat hooks.
- local-player 3D scene HUD elements must not assume they live on the player prefab or let every spawned player claim the shared HUD in `Awake()`. That breaks as soon as the health canvas, reticle, and spawned weapon/ability HUD live in the scene instead of under the ship, and it becomes outright wrong for future networked ownership where only one player on a peer is local. Keep one `PlayerHUDManager3D` on the HUD, let it resolve the local player, and have each HUD element subscribe to that shared binding.
- local-player 3D reticles moved onto the scene HUD must not keep a stale or player-prefab-local aim origin after the component leaves the ship root. The hover hitscan still needs to come from the same camera-centered aim ray the weapons use; otherwise the brackets test one line while the real shots use another. Keep the HUD reticle binding the resolved gameplay camera back into the bound player's weapons so the hover ray and the actual firing path stay aligned.
- local-player 3D weapon select bars must not blindly reuse the reticle's fill semantics for every weapon. The reticle currently uses "resource usage" and "cooldown remaining" style values, but the weapon HUD ask is "resource still available" and "cooldown ready progress." If the HUD reuses the reticle ratio directly, resource bars drain in the wrong direction and cooldown bars read backward. Keep the weapon HUD fill calculation explicit about whether a slot is showing remaining availability or progress back to ready.
- local-player 3D ability select bars must not reuse the legacy `Ability3D.GetHUDFillRatio()` value when the canvas is authored as a ready-progress bar. That older helper reports cooldown remaining, so a copied weapon-style HUD will animate backward unless it reads an explicit cooldown-ready ratio instead. Keep ability HUD fill driven from `Ability3D.CooldownReadyRatio`, and keep the ready flash on the surrounding box rather than on the fill image when that is the authored visual language.

## Current Constraints

Right now, the 3D path is still translating a game originally structured around:

- `Rigidbody2D` gameplay
- a mostly planar duel space
- orthographic combat readability
- 2D-era assumptions in some movement, aiming, and VFX logic

It is also translating into a project that already has an existing networking philosophy and partial implementation.

That means 3D systems should not be engineered as isolated local prototypes first and "networked later" unless the work is explicitly marked as temporary experimentation.
That also means 3D systems should not be engineered as performance-last prototypes if they are expected to survive into shipping code.

That means contributors should assume some systems are still hybrid and incomplete.

Do not describe the 3D path as complete unless the relevant gameplay, UI, and networking path is actually implemented end to end.
