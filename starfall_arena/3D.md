# 3D.md

This document governs the active 3D implementation path for Starfall Arena.

Use this doc whenever work is primarily about translating the current duel game from its existing 2.5D / orthographic presentation into a fuller 3D experience.

If you are working on the 3D implemenation, you should ONLY edit scripts in `Assets/Scripts/3d`. Every other gameplay script is part of the 2.5D game. You may read non-3D scripts for reference, but if a 3D task appears to require edits outside `Assets/Scripts/3d`, stop and ask the user for explicit permission before changing any non-3D code. Documentation updates are still required, but if the needed doc change lives outside the 3D docs, ask permission before editing that non-3D doc as part of a 3D-scoped task.

## Purpose

The goal is not to replace the game's core identity.

The goal is to preserve almost all current duel systems while changing how the game is spatially presented, moved, read, and eventually played in 3D.

That means the 3D effort should generally preserve:

- the duel-first game structure
- the two-player combat focus
- existing ship classes, weapons, abilities, augments, HUD expectations, and round flow unless a change is intentionally required
- controller-first usability
- keyboard-and-mouse support
- the active networking direction
- performance targets appropriate for a PS4 build

The default assumption should be:

- keep the gameplay rules unless 3D implementation makes a rule impossible or clearly harmful
- change presentation, movement interpretation, camera behavior, targeting context, and supporting systems only where needed
- engineer 3D systems in a way that stays compatible with the existing networking direction documented in `NETWORK.md`, instead of creating local-only behavior that will be expensive to retrofit for server-authoritative play later
- engineer 3D systems with performance in mind from the start, especially for PS4-class hardware, instead of assuming expensive effects or allocation-heavy workflows can be cleaned up later

## Relationship To Existing Docs

`GAME_SYSTEMS.md`, `UI_MANAGERS.md`, and `NETWORK.md` still describe the current live game.

`3D.md` exists to document how the 3D implementation should adapt or reinterpret those systems.

When working on 3D features:

- read `3D.md` first
- then read `GAME_SYSTEMS.md` for the underlying gameplay system being preserved
- read `UI_MANAGERS.md` if the 3D work affects HUD, menus, selection flow, or scene flow
- read `NETWORK.md` if the 3D work affects network authority, prediction, sync strategy, or remote presentation
- keep implementation edits inside `Assets/Scripts/3d` unless the user explicitly approves broader changes after the need is identified

If a 3D change directly alters one of those shared systems, update both this file and the affected subsystem doc.

## Current 3D Direction

The current 3D effort should be treated as an implementation track for the same game, not as a separate game mode.

The intended direction is:

- move from orthographic 2.5D presentation toward a perspective-driven 3D experience
- preserve combat readability and fast duel clarity
- preserve current game logic where possible
- replace only the assumptions that are specifically tied to the 2D plane

Current likely focus areas include:

- 3D ship movement and steering
- camera framing and perspective readability
- translating thrust, banking, pitch, and visual feedback into 3D
- adapting aiming, target readability, projectile readability, and combat spacing
- determining which existing 2D physics assumptions can remain and which need true 3D replacements

## Current 3D Architecture

The 3D ship path now uses the same identity split as the 2D game, but the real behavior is distributed across focused components instead of being concentrated in one movement script.

```text
Entity3D
  -> Player3D
  -> Enemy3D
```

These classes should stay narrow and mainly coordinate dedicated 3D systems.

Current shared 3D ship systems:

- `ShipFlight3D`
  - shared rigidbody flight
  - thrust, yaw, pitch, friction, and max-speed clamping
  - reusable by local player, AI, or future network drivers
- `ShipVisualTilt3D`
  - banking and pitch lean on the ship visual model
- `ShipThrusterVfx3D`
  - thrust-driven thruster playback and intensity
- `ShipSpeedFx3D`
  - shared speed-based VFX such as dust/trails
- `ProjectileWeapon3D`
  - shared projectile spawn/cooldown ownership for both player and enemy ships
- `StupidTurret3D`
  - scene-test firing driver for stationary or non-piloted 3D ships
  - continuously calls the ship's basic `ProjectileWeapon3D` without producing movement input
  - should be paired with `ProjectileWeapon3D` aim set to `MuzzleForward` when the goal is "fire where the ship is facing"

Current player-only 3D systems:

- `PlayerInput3D`
  - local input adapter
  - feeds movement and weapon systems instead of movement reading raw input directly
- `PlayerCameraRig3D`
  - Cinemachine follow-offset and FOV behavior
  - only belongs on the local player path

Current enemy-only 3D systems:

- `EnemyAIFlightController3D`
  - produces the same movement-intent shape as player input so enemies can reuse `ShipFlight3D`

`Assets/Scripts/3d/Movement3D.cs` now exists as a compatibility coordinator for older prefabs/scenes that were already wired against the previous monolithic script. New 3D work should prefer the componentized scripts directly.

Current 3D projectile split:

- `ProjectileWeapon3D`
  - owns fire cadence, muzzle selection, aim resolution, projectile spawn, and muzzle FX
- `Projectile3D`
  - owns projectile travel, hit detection, hit results, hit FX, and despawn/pool return

For player-facing readability, projectile fire direction should be resolved from the intended aim target, not from a muzzle transform that may be attached under a visually banked or pitched ship mesh.

Current implementation rule for 3D projectile visuals:

- 3D projectile prefabs should stay lightweight visual/data carriers
- if projectile hit detection is already handled by scripted raycasts or sweep tests, do not also add projectile colliders or rigidbodies
- only keep collision components on the real world targets that need to be hittable

This matters for the 3D duel path because projectile counts and VFX density can grow quickly, and redundant per-projectile physics components add cost without improving hit authority when the game is already using explicit hitscan-style evaluation.

## Implementation Principles

When building the 3D version:

- preserve existing gameplay behavior first, then expand
- avoid rewriting stable combat systems just because the presentation changed
- prefer adaptation layers over full-system replacement when possible
- keep inspector-driven tuning for movement, camera, feedback, and combat readability
- preserve controller-first input feel
- do not silently break networking assumptions while experimenting with 3D movement or camera work
- treat networkability as a first-class engineering constraint for 3D work, especially for movement, aiming, combat timing, camera-driven assist logic, and stateful VFX that may need remote presentation
- treat performance as a first-class engineering constraint for 3D work, especially for VFX counts, spawned objects, update-loop cost, memory churn, and expensive camera or physics helpers

3D implementation should stay performant for a PS4-targeted build:

- prefer object pooling over repeated instantiate/destroy loops for gameplay objects and effects
- avoid unnecessary per-frame allocations, transient garbage, or hidden editor-friendly patterns that scale poorly in play
- be careful with particle counts, post-processing, camera effects, and repeated physics queries
- design shared systems so they can scale to real match conditions rather than only working in isolated test scenes
- call out early when a visually attractive 3D feature has a likely platform-cost problem

3D implementation should stay easy to network in accordance with `NETWORK.md`:

- favor deterministic or clearly authoritative gameplay state over presentation-driven hidden state
- keep ownership and authority boundaries clear
- avoid coupling core gameplay results to local camera-only calculations when those results will need to match across clients
- prefer data that can be replicated, predicted, reconciled, or reconstructed cleanly instead of ad hoc local-only behavior
- call out early when a 3D feature probably needs explicit support in the network layer rather than assuming it can be bolted on later

The current component split supports that direction:

- flight intent can come from player input, AI, or future networking drivers without changing the flight system
- camera behavior is isolated from shared ship movement so non-local ships do not inherit hidden local-only state
- projectile firing is owned by a reusable weapon component instead of duplicated across ship types

## 3D Script Folder Layout

`Assets/Scripts/3d` should stay organized by subsystem responsibility instead of collecting every 3D script in one flat folder.

Current folder contract:

- `Core`
  - shared 3D base types and config/data definitions
  - examples: `Entity3D`, `Ship3DTypes`
- `Entities/Player`
  - player-only 3D entity coordination, input, and local camera ownership
  - examples: `Player3D`, `PlayerInput3D`, `PlayerCameraRig3D`
- `Entities/Enemy`
  - enemy-only 3D entity coordination and AI flight intent
  - examples: `Enemy3D`, `EnemyAIFlightController3D`
- `Flight`
  - shared 3D ship movement and reusable flight behavior
  - examples: `ShipFlight3D`
- `Combat`
  - projectile firing, projectile behavior, and other 3D combat-runtime scripts
  - examples: `ProjectileWeapon3D`, `Projectile3D`, `PhysicalProjectile3D`, `Ability3D`, `Beam3D`, `LaserBeam3D`
- `Effects`
  - shared ship presentation and combat/VFX support scripts
  - examples: `ShipVisualTilt3D`, `ShipThrusterVfx3D`, `ShipSpeedFx3D`
- `Effects/ShaderControllers`
  - shader-driven 3D effect controllers
  - examples: `LightningBolt3D`
- `Pooling`
  - shared 3D object-pool helpers
  - examples: `GameObjectPool3D`, `PooledObject3D`
- `Legacy`
  - temporary compatibility shims kept only to avoid breaking older prefabs/scenes during the 3D transition
  - examples: `Movement3D`

When adding a new 3D script, place it under the subsystem it serves first. Do not add new scripts back into the root `Assets/Scripts/3d` folder unless the folder structure is being intentionally redesigned and this doc is updated with that change.

3D work should explicitly call out when it is:

- purely visual
- a control-feel change
- a camera/readability change
- a real gameplay-rule change
- a networking-impacting change

## 3D Ability System

The 3D ability system mirrors the 2.5D pattern: `Entity3D` holds an array of 4 optional `Ability3D` slots, each a MonoBehaviour component on the same GameObject. `PlayerInput3D` routes `OnAbility1`–`OnAbility4` input callbacks to the corresponding slot.

Core architecture:

- `Ability3D` — base class in `Combat/`. Provides `TryUseAbility(InputValue)` input routing, optional cooldown/duration query hooks, lock/disable flags, rotation/thrust multipliers, HUD state hooks, and helpers to check/disable sibling abilities.
- `Ability3D` input rule — the base class is responsible for press-vs-release routing. Hold/release abilities should use base hooks such as release handling and optional timestamp gating instead of replacing the entire input path unless there is a concrete reason the base contract is still insufficient.
- `Entity3D` — owns `Ability3D[] abilities` (size 4), assigned in Inspector. Calls `Die()` on each ability during entity death.
- `PlayerInput3D` — routes ability input to `Entity3D.GetAbility(index)?.TryUseAbility(value)`.

Current ability implementations:

- `Beam3D` — hold-to-fire continuous beam (Class1 Ability 1). Uses capacity system (drain while firing, regen while idle). Spawns a `LaserBeam3D` prefab as a child of the entity.
- `LaserBeam3D` — beam weapon runtime. Drives a LineRenderer + optional impact/muzzle particle transforms from F3D asset pack visuals. Uses camera-center aiming (same pattern as `ProjectileWeapon3D`). Applies continuous DPS via `Entity3D.TakeDamage()`, triggers shield hit effects at intervals. No dependency on F3D scripts.
- `Reflector3D` — Class1 reflect ability for the 3D path. Owns cooldown, active window, and projectile reflection rules.
- `ReflectShield3D` — shield-mesh runtime used by `Reflector3D`. Preserves the 2.5D shield fade/ripple shader behavior and applies the reflected projectile state after the ability approves the hit.

Beam aim direction rule: `LaserBeam3D` resolves aim from camera center (`Camera.ViewportPointToRay(0.5, 0.5)`), not from `transform.forward`. This matches the projectile weapon rule — visual banking/pitching can rotate the beam's parent transform away from where the player is actually aiming.

- `GigaBlast3D` â€” Class1 charged projectile ability for the 3D path. Holds to charge through four tiers, applies tier-based thrust/rotation penalties while charging, and fires tier-specific projectile prefabs through `ProjectileWeapon3D` so the shot reuses the 3D muzzle and camera-aim rules.
- `GigaBlastProjectile3D` â€” optional projectile runtime for GigaBlast tiers that need piercing. It preserves the normal `Projectile3D` hit path, but lets high-tier shots continue through multiple valid ship targets while reducing damage after each hit.

## Documentation Rules For 3D Work

When a change is specific to the 3D implementation path, document it here.

When a change modifies shared game behavior, also document it in the shared gameplay/UI/network doc that owns that behavior.

When a 3D change creates new networking constraints, prediction requirements, replication needs, or authority questions, also update `NETWORK.md`.

Bug notes for 3D implementation should be written here when the issue is mainly caused by the 3D translation layer.

Keep 3D bug notes short and actionable:

- what failed
- why it matters in the 3D path
- how to avoid repeating it

Bug note:

- shared 3D movement scripts must not own local-player camera logic. The earlier `Movement3D` mixed universal flight with Cinemachine behavior, which made enemy or future network-driven ships inherit irrelevant camera dependencies. Keep flight reusable and keep camera behavior on player-only components.
- shared 3D projectiles must not trust a tilted visual muzzle's forward vector for player aiming. Once banking/pitching is applied to the visual model, muzzle children can tilt away from the real gameplay aim. Resolve player projectile direction from camera aim or another authoritative target point, then spawn from the muzzle position using that direction.
- shared 3D projectiles must not carry redundant physics components when the hit path is already explicit hitscan/sweep logic. The earlier 3D projectile version kept a projectile collider even though collision results were being decided by scripted casts. That added avoidable component cost and blurred the true ownership of hit detection. Keep the projectile prefab visual-only unless a real gameplay requirement needs its own physics body.
- shared 3D flight must not let pitched root rotation leak into a duel-plane movement basis. An earlier `ShipFlight3D` version used the ship's full `transform.forward` for thrust, recoil, and speed evaluation, so rotating the ship off the horizontal plane silently injected world `Y` velocity and looked like gravity was turning on during turns. Keep duel-plane movement projected onto a stable world plane and explicitly zero vertical drift when this path is meant to stay planar.
- shared 3D entities must own shield state and the `ShieldController` reference directly, just like the 2.5D `Entity` path. The earlier `Entity3D` only tracked hull health, so 3D projectiles skipped shield absorption entirely and never triggered the canonical field flicker on hit. Keep shield consumption and shield-hit visual triggering inside `Entity3D.TakeDamage(...)` so every 3D ship reuses the same hook-up pattern.
- shared 3D projectiles must resolve the owning `Entity3D` from the hit collider's rigidbody or parent chain before deciding whether damage should apply. In the 3D scene, shots can hit child colliders such as shield meshes or visual model colliders that are intentionally untagged. If `Projectile3D` only checks the exact hit collider for both tag matching and `Entity3D`, the projectile despawns without ever calling `TakeDamage(...)`.
- shared 3D hold abilities such as `Beam3D` must not inherit tap-ability cooldown gating from `Ability3D.TryUseAbility(...)`. That base path timestamps the press event, which is fine for tap abilities but wrong for hold/release weapons and can look like the beam randomly expires or has a fake regen delay before it can fire again.
- shared 3D beam capacity is an overheat meter, not remaining fuel. If `drainRate <= 0` or `capacity <= 0`, the 3D beam should be treated as non-draining and the HUD/resource gate should stay inactive instead of accumulating invisible heat.
- shared 3D reflect shields cannot rely on `OnTriggerEnter`-style callbacks from the projectile itself when the projectile path is explicit sweep logic. `Projectile3D` decides hits by spherecasting and may not carry a live collision body, so the reflect path has to be checked from `Projectile3D.ProcessHit(...)` before normal damage/despawn logic runs.
- shared 3D reflect shields must not treat reflection as a simple `-direction` flip when the gameplay goal is "send the shot back to who fired it." In full 3D space the attacker can sit above, below, or offset from the incoming path, so a planar reversal can miss even though the parry looked correct. Resolve the reflected heading from the projectile position to the original shooter when that shooter still exists, and only fall back to a raw reverse vector if that ownership context is gone.
- shared teleport abilities reused from the 2D path must not keep `transform.up` movement, `z` pinning, or `Collider2D`-only disable/restore logic once they are placed on 3D ships. That combination makes the ship blink but still teleport in the old 2D axis basis, leaves 3D colliders active during the warp, and can restore the wrong post-teleport scale if the mesh prefab is authored with non-unit local scale. Resolve teleport travel from the ship's planar 3D forward, preserve the 3D flight-plane axis, and cache/restore both 2D and 3D presentation state.
- shared 3D ability hooks must be consumed by the movement and firing drivers, not just exposed on `Ability3D`. Before `GigaBlast3D`, the 3D runtime defined thrust multipliers, rotation multipliers, and primary-fire locks, but `ShipFlight3D`, `PlayerInput3D`, and the enemy fire loop never read them. That made charge penalties and fire suppression look configured in the ability while doing nothing in play. Keep the runtime querying `Entity3D` for combined ability state whenever a new 3D ability relies on those hooks.
- shared 3D charged projectiles must not assume every tier prefab shares the same pivot length. `GigaBlast3D` can swap between very short and very long projectile meshes, and some of those prefabs use a midpoint pivot. If every tier uses the same spawn distance, long shots can spawn back through the ship even though short ones look correct. Keep per-tier forward spawn compensation exposed in the ability config when the projectile art varies by tier.
- shared 3D visual tilt must not derive recoil pitch only from total forward acceleration. In the 3D flight path, weapon recoil is injected as a velocity impulse, so folding it into the same signed acceleration term as thrust can invert the feel and removes any independent tuning. Keep thrust pitch and recoil pitch as separate inputs, with recoil sensitivity exposed on `Entity3D`.

## Current Constraints

Right now, the 3D path is still translating a game originally structured around:

- `Rigidbody2D` gameplay
- a mostly planar duel space
- orthographic combat readability
- 2D-era assumptions in some movement, aiming, and VFX logic

It is also translating into a project that already has an existing networking philosophy and partial implementation.

That means 3D systems should not be engineered as isolated local prototypes first and "networked later" unless the work is explicitly marked as temporary experimentation.
That also means 3D systems should not be engineered as performance-last prototypes if they are expected to survive into shipping code.

That means contributors should assume some systems are still hybrid and incomplete.

Do not describe the 3D path as complete unless the relevant gameplay, UI, and networking path is actually implemented end to end.
