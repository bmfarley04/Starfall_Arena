# 3D_BUGS.md

This document is the 3D implementation bug ledger.

Use it for short, actionable notes about regressions, pitfalls, and architectural gotchas that are specific to the 3D translation layer.

Bug note format:

- what failed
- why it matters in the 3D path
- how to avoid repeating it

## Enemy Movement And Steering

- 3D Invasion enemy spawns must not trust authored spawn points blindly. Formation slots, boss points, and carrier-spawner anchors can land inside asteroids, debris, or crippled-ship colliders, and once the enemy is instantiated there the arrival/AI/steering layers are already too late to prevent a bad spawn. Keep the spawn-clearance overlap check inside `InvasionWaveManager3D.SpawnEnemyAt(...)`, tune the blocking layer mask to solid world blockers, and skip with a warning if no nearby clear position exists.
- shared 3D upright recovery must correct signed roll around the ship's current forward axis instead of chasing a rebuilt `LookRotation` target. The target-quaternion path can make the ship roll the long way around, such as taking a 350-degree correction when a 10-degree correction is available. Measure the projected current-up to projected world-up signed angle around forward, clamp that signed delta by recovery speed, and apply only that roll step.
- 3D enemy obstacle avoidance should stay inspectable before it becomes clever. The old `EnemyObstacleAvoidance3D` blended five spherecast probes, hit normals, and hit-point offsets without a stable side choice, which made large-obstacle steering hard to reason about and left the component effectively unused. Prefer a simple forward-blocked check, explicit right/left/up/down escape sampling, and short escape-side memory before adding richer pathing layers.
- Do not smooth all enemy movement at the `EnemyAIFlightController3D` level just to make obstacle avoidance prettier. Rammers, formation ships, and boss movement often rely on sharp committed vectors or authored state-machine paths, so broad motor smoothing can quietly change enemy identity and combat timing. Smooth obstacle arcs inside `EnemyObstacleAvoidance3D` first, then extract a reusable steering smoother only if non-obstacle chase curves become a deliberate design goal.
- General enemy steering smoothing must remain a final opt-in direction filter, not hidden tactical AI. If `EnemySteeringSmoother3D` starts changing speed, facing, range bands, or attack timing, it can silently alter enemy difficulty and identity. Keep speed/facing decisions in brains and `EnemyAIFlightController3D`; use the smoother only to polish final movement direction changes on eligible prefabs.

## Damage And Combat Ownership

- networked 3D player prediction must sweep against authored world blockers before applying the predicted position. The local-only path drives `Rigidbody.linearVelocity`, so Unity contact solving stops ships on asteroid/debris colliders, but `NetMovement3D` advances a pure replay state and applies the target position directly. Without a blocker sweep, both owner prediction and server authority can keep moving through `blocker`-layer asteroids or destroyed ships even though the same colliders work in local test scenes. Keep the network movement blocker mask limited to solid arena blockers and clamp/slide the prediction state when a sweep hits.
- networked 3D enemy proxies are kinematic on clients, so `NetEnemyMovement3D` must not write `Rigidbody.linearVelocity` while interpolating remote snapshots. Unity rejects velocity writes on kinematic 3D bodies, which logs every fixed tick and can hide real networking issues. Keep enemy velocity authoritative on the server; clients should apply sampled position/rotation only and let future presentation systems read snapshot velocity from a non-physics telemetry path if needed.
- 3D combat force code must not write directly to a target `Rigidbody.linearVelocity` before checking for `NetMovement3D` or kinematic state. Networked remote player proxies and client enemy proxies are intentionally kinematic, so projectile, beam, ram, and tractor effects should route through the network movement helper when present, and only use raw Rigidbody velocity writes as a non-networked dynamic-body fallback.
- player-prefab 3D dodge routing must not infer "this dodge is the Class 4 ability" just because a `Dodge3D` component exists on the same ship. The generic left-stick flick dodge and Class 4 ability dodge share the same movement/network pipeline, so the request must carry an explicit dodge kind from input through authoritative resolution and remote presentation. Otherwise Class 4's normal dodge silently inherits the ability's cooldown, distance, and behavior.
- networked 3D proxy movement must not interpolate only between the newest two snapshots. That makes packet cadence jitter visible as small pulses even on low ping, because every late/early packet changes the interpolation endpoints immediately. Keep remote players and server-owned enemies on a buffered server-timeline delay, choose snapshots around the render tick, and expose buffer starvation/extrapolation diagnostics for playtests.
- networked 3D remote player proxies are intentionally kinematic, so interpolation and `ShipFlight3D.ApplyExternalSimulationState(...)` must not write `Rigidbody.linearVelocity` on those bodies. Move/rotate the kinematic proxy from authoritative snapshots and feed velocity into presentation telemetry instead; reserve Rigidbody velocity writes for owner/server non-kinematic bodies.
- networked 3D combat velocity changes must not mutate `Rigidbody.linearVelocity` and then pass the same delta through `NetMovement3D.ApplyCombatVelocityDelta(...)` unless that helper is explicitly authority-aware for the call site. Most current force values are tuned to zero, so this is usually dormant, but non-zero impact/tractor/beam forces can otherwise look like reconciliation jitter because the local Rigidbody and prediction state may receive the same impulse twice.
- `NetCombat3D` projectile accepted-tick history must cover every `NetProjectileVisualType3D` value. The enum currently includes enemy-specific visual types beyond the original player projectile range, and clamping too-small history arrays can make unrelated visual types share a deduplication slot.
- 3D Invasion player respawns must not try to reuse the dead player object after `Entity3D.Died`. The shared 3D death path invokes `Died` and then destroys/despawns the object, so in-place revive code races an object that is already being removed. Capture the death position/rotation in the event, decrement the player's Invasion life count, and spawn a fresh selected player ship at that transform when lives remain.
- Siege Carrier orbital pillar visuals are now owned directly by `SiegeCarrierBossEnemyBrain3D`, not a separate playback component. Do not reintroduce `OrbitalEnergyPillarVisual3D`-style wiring or assign a visual-controller prefab to the boss; configure the launch spear prefab, blue pillar prefab, launch scale, launch offset, and initial growth height on the boss brain itself.
- Siege Carrier-style endless vertical hazards must not use actually infinite gameplay checks or client-side damage. The orbital energy-pillar phase is meant to look endless in world Y and persist after phase transition, but the server should use a very tall bounded capsule and clients should only replay the boss-owned launch spear and pillar prefabs. Keep gameplay half-height finite and profile-tuned, keep pillars fixed at their orbit radius around the boss, and replicate only lightweight phase-start presentation data.
- Siege Carrier orbital pillars should stay visually prefab-driven and should not bring back generated spark fields, carrier links, or procedural pillar lightning. Those extra runtime meshes made the attack harder to tune and more expensive; keep the boss brain responsible only for positioning/scaling the launch spear and blue pillar prefabs.
- Siege Carrier pillar expansion should not be implemented only as a shader reveal when the design calls for launched objects transforming into columns. Scale the pillar prefab's world-Y height from `Initial Growth Height` up to `Damage Half Height * 2` during the expand phase so it grows upward and downward out of the launched spear's target point.
- Siege Carrier orbital pillars are a phase-transition layer, not a one-shot ability. Do not add active/fade duration back to the pillar settings; once spawned, they stay alive around the carrier and slowly orbit until the boss despawns or the component is disabled.
- Siege Carrier orbital pillars are not part of the rotating boss attack sequence or `Forced Pattern For Testing`. Keeping them in the generic pattern enum/dropdown lets the sequencer choose the phase layer like a weapon, which can fire it at the wrong cadence and confuse prefab testing. Keep selectable attacks in their own list and trigger pillars only from the phase-two transition path.
- Siege Carrier phase-transition effects must not be checked only from `StartNextPattern`. If the boss crosses the phase-two health threshold during a long active attack, while out of engagement range, during pattern cooldown, or while `Forced Pattern For Testing` is set, pattern-selection code may not run and the transition layer will appear broken. Check phase effects every authoritative brain update, then let normal pattern sequencing continue separately.
- Siege Carrier orbital pillar gameplay must not be gated by visual prefab assignment. Missing launch/body prefabs should produce a clear one-time warning and skip local visual playback, but the phase state and server-authoritative damage layer still need to activate so a prefab wiring issue does not make the boss phase logic look broken.
- Siege Carrier phase transitions must not be driven from hull health alone when the boss also has shields. The bug was that `SiegeCarrierBossEnemyBrain3D` compared `CurrentHealth / MaxHealth`, so shield-heavy carriers could enter phase two far too early even though most of their total survivability was still intact. Drive the threshold from `(CurrentShield + CurrentHealth) / (MaxShield + MaxHealth)` and keep the debug readout on that same combined-durability ratio.
- shared 3D precision throttle must not hard-clamp existing forward velocity when low positive thrust is applied. The regression introduced in the left-stick precision-throttle path used `Mathf.Min(localVelocity.z, precisionMaxSpeed)` after acceleration, so feathering thrust while already above the precision cap instantly cut speed and looked like the player hit an invisible wall or got jerked backward by reconciliation. Treat the precision cap as an acceleration ceiling from below: stop adding speed once above the cap, but let existing velocity decay only through friction or explicit braking.
- 3D boss bullet-hell patterns must not scale difficulty by uncapped projectile count. A Siege Carrier-style enemy can look interesting with targeted rakes, fans, curtains, and beam convergence, but without explicit shot budgets and authored escape lanes it turns into expensive noise that is harder to dodge and worse for PS4-class performance. Keep each major pattern lane capped per activation, and raise later-phase pressure with cooldown/cadence before adding more bullets.
- Siege Carrier multi-player pattern pressure must keep per-player sequencer state lane-owned. The old single `_activePattern`/step/cooldown state meant a two-player boss could only pressure one player at a time, and global beam/spawn cleanup could stop the wrong attack if parallel patterns were bolted on casually. Future parallel boss attacks should carry their own lane target, timers, step counters, beam counts, and cleanup path.
- boss-specific slow beams should not add slow behavior directly to the shared beam runtime unless every beam in the project needs that rule. `BeamWeapon3D`/`LaserBeam3D` are shared by player, duel, and enemy beams, so adding slow there would silently change unrelated weapons. Keep special-case boss slow owned by the boss brain or another explicit attack driver, and let the beam weapon continue to own only its normal visual/damage/network state.
- Siege Carrier beam patterns should not be described as a curtain/fence unless they actually create navigable lanes. The first beam-fence pass only spread a few lines near the target direction, which did not create a clear dodge challenge and made the expected outcome hard to read. For the current simpler pattern, aim every beam hardpoint at one lagged convergence point and tune lag/smoothing explicitly; save true lane-fence geometry for a later authored pattern.
- Siege Carrier converging beams must not leave explicit boss aim under the beam runtime's forward-only clamp. The brain can calculate a correct muzzle-to-convergence-point direction, but `LaserBeam3D`/`ForgeEnemyBeam3D` may clamp that network/AI aim back to `Direction Reference.forward` when the target leaves the hardpoint's forward hemisphere, making beams look like they fire straight ahead. For boss convergence patterns, enable the explicit behind-hardpoint aim override on the assigned `BeamWeapon3D` components while keeping the normal clamp for beams that should never shoot backward.
- Siege Carrier beam tracking values must be tuned on the active balance profile, not only on the scene/prefab brain component. `EnemyBalanceProfileApplier3D` applies the profile in both `Awake` and `Start`, so component-side beam convergence values can look correct in the Inspector while runtime still uses the asset's lag/smoothing values. For tight tracking, keep the profile's `beamConvergenceLagSeconds` and `beamConvergenceLagBlend` at 0, then add only a small `beamConvergenceAimSmoothTime` for visual stability.
- Siege Carrier rake patterns must not resolve the whole volley from stale target-history samples. That makes the attack feel like it is firing where the player was, not following the player shot-by-shot, and lowering the history delay may still feel weak because the sampling cadence is another source of lag. Resolve each rake shot at fire time from the current target position/velocity, then blend toward history only when a deliberate trailing effect is wanted.
- Siege Carrier-style bosses must not treat hull facing as their primary aim contract. If the boss continually rotates its huge body to face the player, it reads like a normal chaser and can make broadside/beam hardpoints visually unstable. Keep the hull focused on range maintenance, preserve its movement plane where possible, and let pattern weapons aim at the player's world position.
- multi-beam 3D enemies must not let client cosmetic replay resolve every beam through the first `BeamWeapon3D` component. That works for single-beam enemies, but a beam convergence pattern with several hardpoints will show the wrong source or overwrite another beam on remote clients. Include a stable beam component index in enemy beam state/aim RPCs and keep the prefab's beam component order identical across host and client.
- simultaneous formation missile salvos must not reuse the normal `EnemyMissile` visual type when an enemy can also carry regular missile launchers. `NetEnemyCombat3D` resolves client cosmetic projectile replay by visual type, so sharing the type can make remote clients spawn the wrong missile prefab or miss the formation data. Give shaped salvos their own visual type and serialize the formation slot/count/timing needed for clients to reproduce the same fan-and-collapse path.
- boss missile blooms must not count as a single projectile just because they come from one weapon activation. An eight-missile convergence pattern creates eight live guided objects and a much harder dodge check, so charge the boss projectile budget by missile count and keep the salvo count low enough for PS4-class performance.
- formation missile salvos must not use one fixed cruise speed and one fixed timing profile for every slot and range. Ring slots have different curved path lengths, so equal speed makes arrivals stagger one after another; close-range targets also make long fan/hold timings overshoot the useful dodge window. Give the salvo distance-scaled timings and let formation missiles adjust collapse speed toward a shared arrival window.
- enemy missile weapon variants must not inherit a base `DisallowMultipleComponent` when bosses need several missile behaviors on the same root. Unity treats subclasses as the base type for this restriction, so `StaggeredMissileWeaponEnemy3D` can block adding `FormationMissileSalvoWeaponEnemy3D` even though they are distinct weapon components. Put duplicate-prevention only on leaf components that truly cannot coexist, not on reusable weapon bases.
- Flamethrower enemy damage must not stay as a rigid forward cone when the visual particle plume inherits lateral emitter movement, but it also must not use only the final drifted centerline. During orbit/strafe, new flame exits along the muzzle while older particles drift sideways with Rigidbody velocity; checking only one line makes a stationary player receive partial damage from a full visible burst. Keep the authoritative query as a swept volume between the fresh muzzle lane and the drifted particle lane, and calculate tick damage from actual elapsed time so frame timing does not undercount DPS.
- Flamethrower profile weapon stats must not be hidden inside the brain-stat application path. If `damagePerSecond`, burst duration, range, or drift tuning only change on `EnemyFlamethrowerWeapon3D` but not from `FlamethrowerEnemyBalanceProfile3D`, profile tuning becomes misleading and prefab inspector values silently win. Apply flamethrower weapon stats through the profile weapon-stat hook, then apply brain movement stats separately.
- Duelist-style 3D enemies must not reroll weapon choice every think tick without a commitment window. The original `DuelistEnemyBrain3D` could pick missile, beam, projectile, then beam again across adjacent 0.06s decisions, which visually flickered weapons and let the enemy dodge around intentional beam slowdown/readability costs. Keep a serialized weapon commitment duration and, while that commitment is active, either keep using that weapon if it is still valid or hold fire instead of immediately switching.
- Duelist-style 3D enemies must not make repositioning a no-combat waiting room. The original perch state could spend several seconds flying to a perch or waiting for `maxRepositionDuration` before `BeginEngage`, even when the player was already detected and in a valid weapon range. Reposition/perch movement may change where the enemy flies, but valid weapon fire should still be evaluated so acquisition and perch refresh do not look like the AI is thinking for several seconds.
- Duelist-style 3D enemies need explicit range-correction movement outside the preferred pocket. If a detected target is beyond `preferredRangeMax`, the duelist should directly approach; if the target is inside `preferredRangeMin`, it should keep facing the player while backing away. Do not rely on a flank-perch path to solve close-range or out-of-range correction, because that can suppress fire and read as indecisive movement.
- Duelist-style 3D enemies must not use the forward-only enemy flight motor for target-facing lateral perch movement. `EnemyAIFlightController3D` only applies velocity when its forward/backward facing is aligned with the requested move direction, so "move to this side perch while facing the player" often becomes zero velocity and makes the enemy sit still. For flankers that must keep aiming at the player while moving sideways, store target-relative perches and drive preferred-band relocation through `EnemyStrafeMover3D`; reserve the flight controller for direct approach, backing away, and facing.
- 3D Invasion projectile enemies must not treat aim tolerance as projectile spread. The bug was that brains such as the artillery fortress and glass cannon interceptor waited until the nose was within a few degrees of the player, then fired strictly muzzle-forward; at 100-200m that remaining 4-8 degrees is enough to miss by a large distance. Enemy aim tolerance should gate permission to fire, while direct-fire brains pass the target or locked lead direction into `ProjectileWeaponEnemy3D` / `NetEnemyCombat3D` so the projectile launches along the intended shot line.
- 3D Invasion heavy cannons with large muzzle offsets must not lock only a root-to-target direction when the intended shot is a precise charged blast. Even after the muzzle-forward bug is fixed, firing a root-resolved direction from an offset cannon creates a parallel line from the muzzle, so a stationary player can be missed by the muzzle offset. When the brain has a locked current/lead point, fire through the convergence-point projectile path so each muzzle resolves its own muzzle-to-point direction.
- warning-sphere telegraphs must not follow the player live while the underlying charged attack still locks stale aim or stale target ownership. The old glow-only telegraph path was honest enough when it only meant "an attack is charging," but a sphere on the player reads as "this exact player is still the chosen target right now." If the sphere follows one player while the charge re-targets, or if the sphere follows live movement while the shot still uses a frozen charge-start direction, the telegraph looks correct and feels unfair. Keep sphere-enabled attacks target-locked to one entity for the full windup, resolve the live target anchor through `Player3D.WarningSphereAnchor`, and only preserve fully locked aim on non-sphere telegraphs.
- 3D Invasion death-spawn enemies must route child spawns through `InvasionWaveManager3D` instead of calling `Instantiate` directly from the dying enemy. Direct child instantiation can make wave completion fire early because the manager only waits on enemies it tracks. Use the manager's spawn API so Splitter children are added to alive-enemy tracking and network-spawned the same way as wave enemies. When the child uses the same prefab at a different scale/role, apply that configuration before `NetworkObject.Spawn(...)` and synchronize role/scale to clients so they do not render full-size parent hybrids.
- 3D Invasion wave authoring must not stay as one flat enemy list spawned at one exact point. The old wave shape only knew `{prefab, count, delay}` and reused one raw spawn position/rotation per enemy, so multi-enemy groups stacked on top of each other and mixed-type formations were impossible to author cleanly. Keep formation generation in `InvasionWaveManager3D` and still route every real spawn through `SpawnEnemyAt(...)` so tracking, NGO spawning, HUD counts, and death-spawn children stay centralized.
- hybrid 3D enemies that choose between projectiles and artillery-style beams must keep their brain aim contract aligned with the beam runtime. `ForgeEnemyBeam3D` can follow its authored hardpoint transform, so a brain that validates against ship-to-target direction but then uses a hardpoint-following beam can start a beam that visibly points away from the player. Match `ArtilleryBeamEnemyBrain3D`: gate beam fire against `BeamWeapon3D.GetBeamForwardDirection()` and update the beam with that same hardpoint direction. Do not silently fall back to projectiles after choosing beam during debugging, or it hides whether the beam choice is being blocked.
- authored enemy beam muzzles can have correct positions but wrong local forward axes. A blocked-beam log such as `fireDir=(0, -1, 0)` with a roughly 90 degree aim error means the beam weapon is reading a transform whose +Z points down, even if the mesh looks visually aimed at the player. Keep `Muzzle` as the origin and assign `BeamWeapon3D.Direction Reference` to a clean forward-facing transform so AI gates, gameplay raycasts, and Forge/Laser visuals consume the same direction.
- multi-muzzle enemy projectile volleys should not always reuse one shared forward direction when the hardpoints are far apart. Wide muzzles fired in parallel can look like the enemy is missing on both sides even when the chosen attack is correct. For enemies such as the Splitter, aim each muzzle toward a shared convergence point in front of the ship and expose that distance for tuning.
- 3D Invasion enemies must not target a generic `"Player"` tag. The 3D project currently defines `Player1`, `Player2`, and `Enemy`, so generic player-tag lookups leave enemies with no target and make projectiles appear broken. Use `FactionMember3D` / `Faction3D.PlayerTeam` for PvE targeting and keep tags only as fallback compatibility.
- 3D Invasion beam enemies must not stay tag-only even if the older duel beam path did. `LaserBeam3D` originally only validated hits against `targetTag`, which made a translated artillery enemy appear to aim and fire correctly while silently never damaging co-op players because there is no generic `"Player"` tag. Give PvE beams an explicit `targetFaction = PlayerTeam` and only use tags as compatibility fallback.
- networked 3D player beams must not blindly rewrite generic `"Enemy"` targeting into duel opponent tags on authoritative start. The bug was that `BeamWeapon3D` and `ConvergeBeamWeapon3D` saw `targetFaction = Neutral` during network play and always swapped their runtime target tag to `Player1`/`Player2`, which is correct for duel-only beams but wrong for Invasion. That made a remote client's local beam cosmetic appear to hit enemies while the server-owned damage beam was silently filtering for the other player tag instead. Resolve player weapon targeting through the same duel-vs-Invasion logic used by `NetCombat3D` so generic enemy targeting upgrades to `EnemyTeam` when PvE enemies are present and only falls back to duel tags when no enemy-team targets exist.
- Forge3D beam prefabs must not own gameplay raycasts when used in the 3D combat path. `F3DBeam`/`F3DLightning` already raycast, scale the line, move impact/muzzle anchors, and may apply force every frame, so letting them stay authoritative alongside `LaserBeam3D` or `ForgeEnemyBeam3D` duplicates hit detection and breaks network/cosmetic separation. Reuse Forge assets through the 3D beam runtime or a cosmetic-only link driver, and keep stock Forge raycast scripts disabled on gameplay beam prefabs.
- Forge3D warp-jump prefabs may ship with debug looping enabled. If `DebugLoop` stays on, an Invasion spawn arrival effect can replay during runtime testing instead of behaving like a one-shot enemy entrance. Route warp-in prefabs through `SpawnArrivalEffect3D`, which disables the loop on spawned instances, and keep the effect cleanup path attached.
- Forge3D warp-jump particle systems can use `ParticleSystemScalingMode.Shape`, which makes transform scale affect emitter shape but not particle size. If an Invasion arrival effect stays huge after tuning prefab or multiplier scale, force hierarchy scaling on the spawned particle systems and preserve the prefab root scale before applying any extra multiplier.
- portal visuals must not stay transparent-only when a boss is supposed to emerge half-hidden from another dimension. `Portal3D` originally looked correct as a glowing surface, but transparent portal pixels do not write depth, so the full boss mesh stayed visible through the effect while moving forward. Keep a portal-sized depth-mask disk in the portal prefab whenever `PortalBossSpawn3D` is used, and tune portal scale large enough to cover the boss silhouette because this masking path is intentionally silhouette-approximate rather than an exact per-material clip plane.
- large portal-spawn bosses must not treat the authored spawn point as the portal plane when the root/pivot is near the visual center of the ship. The first `PortalBossSpawn3D` pass moved the center to the final point and then shrank the portal, which made long ships look like the portal closed while their rear half was still inside it. Keep the authored spawn point as the final boss center, but place the portal backward by the render-bounds rear extent along boss forward so the portal stays open until the tail clears.
- Forge-style lightning prefabs must not leave secondary line renderers outside the unified beam runtime. The Triumvirate final beam could damage the player through the intended ray while a child lightning renderer still pointed along stale prefab/local-forward data, making the visible beam disagree with gameplay. Register every authored gameplay line renderer on `ForgeEnemyBeam3D.additionalLineRenderers`; `ForgeEnemyBeam3D` also auto-registers child line renderers outside muzzle/impact effect anchors as a safeguard. Let explicit AI/network aim resolve before the hardpoint-forward fallback when a coordinated attack needs beams to converge.
- Forge-style lightning UV scrolling must not hard-reset on a short timer. Resetting the material offset every second is easy to miss while the target is moving because endpoint and jitter motion hide the snap, but against a mostly stationary player it can look like the beam texture flips or bunches into the impact effect. Let the UV time accumulate continuously so texture repeat handles wrapping without a visible discontinuity.
- Forge-style lightning line renderers should be driven in world space when the prefab has child line-renderer transforms. Feeding root-local points to child renderers assumes every controlled renderer has the same local origin/rotation as the runtime root; that can collapse or misplace visible strands while muzzle/impact effects still appear correct. Prefer `ForgeEnemyBeam3D` world-space line points for gameplay lightning beams and keep muzzle/impact particles on their anchors.
- Triumvirate ship-to-ship links should not manually imitate the Forge lightning prefab if the final beam already uses `ForgeEnemyBeam3D`. A hand-driven line can miss material UV scrolling, place muzzle/impact child effects at the wrong relative point, or get out of sync with extra child line renderers. Use `ForgeEnemyBeam3D.StartCosmeticLink(...)` so the cosmetic link shares the same visual anchor and material update path as the real beam while still applying no damage.
- charge telegraph emission sliders must not become the renderer's permanent baseline. `ArtilleryFortressChargeTelegraph3D` is reused by enemies with authored idle glow, so `Idle Emission Intensity` and `Max Charge Emission Intensity` should only shape the active warning ramp. Snapshot and restore each renderer's original property block/light intensity when charging ends so a max charge value does not leave the ship permanently over-bright.
- charge telegraph auto-collection must not write black emission into shield or transparent effect materials. Some child materials expose `_EmissionColor` but have black authored emission, so scaling them during a charge can null out their intended shader look. Keep `Only Affect Authored Emission Renderers` enabled when auto-collecting, or explicitly assign only the ship glow renderers that should brighten.
- 3D Invasion enemy prefabs must still keep the root `Enemy` tag until every player weapon/beam path is fully faction-authored. The current 3D combat stack mixes explicit faction checks with legacy `"Enemy"` tag compatibility on several player weapons, so leaving an enemy root `Untagged` can make some attacks damage it while other attacks appear to stop working mid-fight. Keep `FactionMember3D = EnemyTeam`, but also keep the prefab root tagged `Enemy` for compatibility.
- 3D PvE projectiles must not reuse the duel-only "opposite player tag" targeting path. `NetCombat3D.ResolveEnemyTag()` is correct for player-vs-player duels but wrong for co-op Invasion, where both players are allies and enemies should target `PlayerTeam`. Use enemy-specific combat brokering through `NetEnemyCombat3D`.
- networked 3D enemies must not resolve every cosmetic projectile RPC back through `Enemy3D.PrimaryWeapon`. That worked only while enemies had one projectile weapon type; once a tank launched missiles from a separate secondary weapon, remote clients would spawn the wrong prefab or no projectile at all because the RPC replay path always assumed slot 0. Resolve enemy cosmetic projectile prefabs from the firing enemy weapon's own visual type instead of a hard-coded primary-weapon fallback.
- enemy-only 3D projectile launchers must not inherit shot velocity only from `ShipFlight3D`. `Enemy3D` disables the player flight motor and moves through `EnemyAIFlightController3D`/`Rigidbody`, so reading launch velocity from `ShipFlight3D` alone makes moving enemies fire shells and missiles as if they were standing still. Enemy weapon launch velocity should come from the active Rigidbody path instead.
- 3D player projectiles must not infer PvE targeting only from the shooter's `PlayerTeam` faction. The same player prefabs can still participate in duel flows, so `NetCombat3D` should preserve opposite-player targeting unless the projectile request explicitly carries a non-neutral target faction.
- networked 3D enemies must not run AI on every peer. If clients also choose targets, steer, or fire, enemy movement and damage can diverge immediately. Keep enemy brains server-only in networked Invasion and replicate movement/cosmetics outward.
- networked 3D enemy charge tells must not be driven only by server-side brain state. Clients do not run enemy AI, so a windup glow or VFX started only from the authoritative brain can be invisible on remote machines even though the projectile later appears correctly. Keep the gameplay decision server-only, but replicate lightweight presentation start/stop state for telegraphs such as `ArtilleryFortressChargeTelegraph3D`.
- networked warning-sphere telegraphs must not replicate only "start charging now" without also identifying which player entity owns the sphere follow target. In co-op Invasion, clients do not run the enemy brain, so a replicated timer alone is not enough once the telegraph has to follow a specific player's visual anchor. Replicate the intended target network object id alongside telegraph timing, then resolve that player's explicit warning anchor on each peer so the sphere shrinks on the same ship everywhere.
- enemy charge telegraphs must not be treated as self-firing weapon components. The original artillery charge tell only changed renderers/VFX and worked because `ArtilleryFortressEnemyBrain3D` explicitly called it during the cannon state machine; adding the visual component to a basic enemy did nothing because no brain or weapon driver was starting the tell or delaying fire. For reusable projectile or missile windups, pair `ProjectileChargeTelegraph3D` with a brain hook or `EnemyProjectileChargeAttack3D`, and assign the actual `IEnemyProjectileWeapon3D` component there.
- Flamethrower charge windups must be started by `FlamethrowerEnemyBrain3D`, not only added to the prefab. `EnemyProjectileChargeAttack3D` is a generic weapon gate: it plays the telegraph, waits, then starts the selected weapon, but it does nothing until a brain calls `TryBeginCharge(...)`. Keep the charge driver's `Weapon Type` set to `Flamethrower` and let the flamethrower brain call it instead of starting the burst directly.
- 3D siege enemies must not rely on target-sensor radius as their only attack range. A high sensor radius is useful for acquisition, but if firing only checks aim/cooldown, the enemy effectively shoots from arbitrary distance and feels unfair. Keep a separate weapon engagement range, and use a limited approach buffer when the enemy should move into range.
- multi-launcher enemy missile racks should not use the base all-muzzle volley when the intended read is a staggered rack. Dumping every guided missile on one frame makes close-range pressure spike too hard and hides the launcher sequence. Use `StaggeredMissileWeaponEnemy3D` when each authored launcher transform should fire one at a time; keep the inherited weapon cooldown as the full rack cooldown and use `launcherStaggerInterval` for the delay between individual missiles.
- 3D missile weapons should not use the generic projectile muzzle-FX path. Missile prefabs already own exhaust, trails, delayed renderer despawn, and impact presentation, so extra generic muzzle flashes create duplicated launch feedback and unnecessary pooled objects. Keep missile launch visuals on the missile prefab or a missile-specific launcher child VFX, not the shared gun muzzle-FX fields.
- Unity custom inspectors must use public editor drawing APIs. Calling inaccessible editor helpers can break the editor assembly while the runtime assembly still looks fine from a normal player-code build, which leaves Inspector UI stale and can hide newly serialized fields such as missile stagger settings. Compile `Assembly-CSharp-Editor.csproj` when changing Editor-folder scripts.
- child launcher tracking should not become a second AI brain. Rotating missile-rack model pivots toward the player is useful readability and can align hardpoint visuals, but target choice and fire cadence still belong to the enemy brain/weapon gate. Keep launcher trackers presentation-focused, yaw-only when the model requires it, and do not let them apply damage or decide when to shoot.
- enemy prefabs with both a heavy cannon and small laser-bolt turrets must not put both weapons on the same enemy projectile visual type. `NetEnemyCombat3D` resolves client cosmetic projectile prefabs by visual type, so two different projectile weapons sharing `EnemyProjectile` can replay the wrong prefab on remote clients. Use `StaggeredProjectileWeaponEnemy3D` / `EnemySecondaryProjectile` for secondary turret bolts when the heavy cannon already uses `ProjectileWeaponEnemy3D`.
- two-part turret models should not rotate the whole turret object to solve both yaw and elevation if the mesh is authored as a yaw base plus a pitch child. That makes the base tilt or the barrel yaw in the wrong local space. Use `ProjectileTurretYawTracker3D` bindings so the base owns local Y yaw and the child barrel/head owns local X pitch, with offsets/inversion for model-axis differences.
- side-mounted turret bases may have a different authored swivel axis than top-mounted bases. If a side base needs local X to face horizontally, enable `Use Base X Rotation` only on that turret binding; do not globally change the tracker axis or the normal top-mounted turrets will start rotating around the wrong local axis.
- 3D enemies must not leave `ShipFlight3D` actively controlling the same Rigidbody as the enemy motor. The player flight path reads player-shaped look/thrust input and can overwrite velocity in `FixedUpdate`, causing enemies with correct targets to drift, orbit, or fly away erratically. Keep enemy movement owned by `EnemyAIFlightController3D`; `Enemy3D` disables `ShipFlight3D` at runtime.
- baseline 3D enemy movement must not preserve old velocity like a player ship. If the motor accelerates/decelerates toward desired velocity, inherited sideways or forward velocity can create wide arcs and make a simple AI look erratic. The default enemy motor should rotate toward the declared direction and directly set velocity along its current forward only when facing that direction.
- baseline 3D enemy movement must not assume "desired facing" and "desired travel" are always the same vector. That assumption works for chasers, but it breaks artillery behavior because the enemy has to keep its nose on the target while backing away to maintain beam pressure. Use an enemy flight contract that can face toward the target while translating backward when a brain needs kiting behavior.
- formation enemies must not ask `EnemyAIFlightController3D` to move toward a slot while facing an unrelated target unless the movement is intentionally backward. The default motor only applies velocity when its forward/backward movement facing is within `moveWhenFacingAngle` of the move direction, so a Triumvirate-style brain that says "move to slot, face player" will rotate toward the player and then sit still forever. Face the slot while traveling, then face the target once the member is inside formation tolerance.
- Triumvirate-style formation centers should not default to a far target-relative anchor during local testing. A fixed center such as "32m from target along the squad-to-target vector" can make the whole group drift away on world Z before climbing into its triangle, which reads like broken steering rather than an attack tell. Keep the default formation anchored near the current squad center, and use small explicit vertical width/height offsets for the two-low / one-high shape.
- Triumvirate vertical slot offsets must be centroid-balanced and member slots must stay stable. If the top slot is `+height` while the lower slots have no matching downward offset, recomputing the formation center from current member positions makes the center climb every frame and the squad appears to rise forever when tolerance is hard to satisfy. Use top `+2/3 height`, lower slots `-1/3 height`, and assign each member a stable top/left/right slot instead of deriving a new role from unstable movement state.
- baseline 3D enemy movement must not evaluate its facing gate from the rigidbody's pre-rotation heading or build `LookRotation(..., Vector3.up)` blindly for near-vertical chase vectors. In 3D Invasion, a fast-retreating target can shift the desired heading every think tick; if the motor checks movement eligibility against the old rotation, or if the target direction is almost parallel to world up, the enemy can get stuck zeroing its velocity while twitch-turning in place. Use the just-computed post-rotation heading for the move gate, and fall back to a stable local up reference when the desired direction is nearly vertical.
- 3D enemy thrusters must not depend only on `ShipFlight3D.IsApplyingThrust`. `Enemy3D` disables `ShipFlight3D`, so enemy VFX should read `EnemyAIFlightController3D.IsMovingForward` when that motor is present.
- 3D enemy visual tilt must not depend on active `ShipFlight3D`. Enemy prefabs keep `ShipFlight3D` only because shared `Entity3D` still requires it, but `Enemy3D` disables it to prevent two Rigidbody owners. Use `EnemyVisualTilt3D` for enemy ships, `ShipVisualTilt3D` for player ships, and never keep both scripts targeting the same `visualModel`.
- 3D enemy brains must not treat a disabled helper component as "off" unless the brain also checks its enabled state or an explicit brain-side toggle. Unity stops `Update`/`FixedUpdate` on disabled `MonoBehaviour`s, but direct method calls still run, so a disabled `EnemyObstacleAvoidance3D` can keep rewriting steering if `BasicShooterEnemyBrain3D` only checks for a non-null reference. Gate optional steering helpers behind an inspector toggle plus `isActiveAndEnabled` when designers need reliable on/off behavior from the prefab.
- 3D contact-attack enemies should not accumulate collision-workaround AI once the underlying collider setup is fixed. The older rammer brain grew reverse-eject steering, collision exemptions, overlap buffers, and swept probes to compensate for bad physical contact. That made the enemy harder to tune and easier to desync mentally from its networked charge identity. Prefer simple server-owned collision/trigger contact for fixed colliders, then apply deterministic velocity deltas through the relevant network movement component.
- 3D contact-attack enemies must not run their ram trigger only on the brain's think interval. At typical `moveSpeed` and a 0.05s think tick the enemy can travel a full `ramDetectionDistance` between ticks and end up inside the target's collider before the hit ever fires. Run the contact range/overlap check on `FixedUpdate` so closure-rate edge cases cannot skip the trigger; keep heavier steering decisions on the cheaper think interval.
- networked 3D combat must not let projectiles, beams, or ability overlap logic apply gameplay damage on every peer. The pre-networked 3D scripts were local-authoritative, so enabling combat input without a broker would make each client simulate its own damage truth. Keep `Projectile3D` / `LaserBeam3D` split into cosmetic-only client instances and server-authoritative gameplay instances through `NetCombat3D`.
- networked 3D round stats must not reuse the 2D `Player` counters or count damage on cosmetic client copies. The 3D path uses `Player3D` / `Entity3D`, and only the server-authoritative damage path knows which shield/hull damage actually applied. Keep 3D stat recording in `PlayerCombatStats3D` and update it from authoritative `Entity3D` damage plus authoritative projectile fire paths.
- shared 3D accuracy stats must not count raw projectiles, muzzles, or beam damage ticks as separate player attempts. Continuous attacks such as beams can apply damage every frame, and multi-muzzle weapons can spawn several hit objects from one button press. Give each real attack attempt one tracked accuracy id, count fired once when the attack starts, and count hit once when the first authoritative damage applies.
- networked 3D player death must not call `Destroy(gameObject)` directly on a spawned player object. NGO despawn is the network-visible operation; direct destroy can leave stale remote player objects, stale tags, and mismatched death presentation. Use server-owned `NetworkObject.Despawn(...)` after broadcasting death effects.
- networked 3D combat impulses must update the movement simulation state, not only the live `Rigidbody`. `NetMovement3D` owns prediction/reconciliation state, so recoil, impact force, tractor pull, and teleport warps can be overwritten on the next tick if they do not also pass through combat velocity/warp helpers.
- networked 3D dash-style movement must be started from replayable movement input, not from a combat RPC side channel. Class 4 dodge previously injected `DodgeVelocity` outside `NetInputSnapshot3D` and also wrote Rigidbody velocity directly, so reconciliation could not replay the same dash and owner clients jittered when server snapshots arrived. Put the dodge request/direction in movement input, let `NetMovement3D` apply it during owner/server/replay simulation, and keep combat RPCs presentation-only.
- networked 3D slow must be treated as server-owned combat state. If the server trusts the owner's submitted slow multiplier, a client can accidentally or intentionally simulate movement with a stale or incorrect debuff state. Server movement simulation should read the server-side `Entity3D` slow value.
- shared 3D victim-hit audio cannot infer beam-vs-projectile behavior after the fact if `Entity3D.TakeDamage(...)` drops the damage source. The earlier contract only passed damage, hit point, and attacker, which meant `Player3D` had no reliable way to decide between shield/hull impact sounds and the looping beam-hit sound. Keep the 3D damage path explicit about source type whenever downstream feedback depends on it.
- shared 3D entities must own shield state and the `ShieldController` reference directly, just like the 2.5D `Entity` path. The earlier `Entity3D` only tracked hull health, so 3D projectiles skipped shield absorption entirely and never triggered the canonical field flicker on hit. Keep shield consumption and shield-hit visual triggering inside `Entity3D.TakeDamage(...)` so every 3D ship reuses the same hook-up pattern.
- local-player 3D shield regen must not assume the 2.5D `Player` timer/rate loop exists automatically after porting to `Player3D`. The 3D player path had shield depletion and shield-hit visuals but no regen timer (`regenDelay`) or per-second refill (`regenRate`), so shields never recovered after combat damage. Keep regen explicitly implemented on `Player3D`, reset the regen timer on incoming damage, and run regen with server authority when NGO is active so proxy HUD shield values stay in sync.
- shared 3D projectiles must resolve the owning `Entity3D` from the hit collider's rigidbody or parent chain before deciding whether damage should apply. In the 3D scene, shots can hit child colliders such as shield meshes or visual model colliders that are intentionally untagged. If `Projectile3D` only checks the exact hit collider for both tag matching and `Entity3D`, the projectile despawns without ever calling `TakeDamage(...)`.
- shared 3D temporary shield abilities must intercept projectiles from the explicit `Projectile3D` hit path rather than relying on passive trigger callbacks from the shield mesh. A Class2 absorb shield can look visually correct as soon as its shield object is active, but explicit spherecast hits still flow into normal damage unless `Projectile3D.ProcessHit(...)` delegates that impact to the ability first. Keep projectile-impact overrides explicit in the 3D projectile runtime whenever an ability is supposed to absorb, redirect, or otherwise replace the default hit result.
- shared 3D debuff projectiles must extend both `Projectile3D` and `Entity3D` when ported from the 2.5D path. A first-pass Class2 empowered shot port can fire the right projectile prefab and still silently drop its slow effect if the 3D path only ports the ability and not the target-side movement scaling. When a 2.5D projectile carries gameplay state such as slow, burn, or pierce decay, audit both the projectile runtime and the target entity runtime before assuming the ability port is complete.

## Flight, Camera, And Control Feel

- Class 4 3D dodge direction must not read `PlayerInput3D.LookInput` when the design expects the next left-stick input. The input asset already binds controller `Look` to `leftStick` and `FreeLook` to `rightStick`, but `PlayerInput3D` originally only consumed `OnFreeLook`, so dodge kept sampling the right stick even though the left-stick action existed. Keep dodge direction on a dedicated left-stick buffer such as `PlayerInput3D.MoveInput` sourced from `OnLook`, and leave free-look on the right stick.
- local-player 3D dodge input should not require a center reset plus a fast threshold crossing before it can reach the actual dodge cooldown gate. That rejected normal controller motions such as holding left/right or rolling directly from right to left with logs like "previous x not reset" and "too slow" even though the intended rule was simply "dodge if the player clearly gives a lateral input and the dodge is not on cooldown." Keep `PlayerInput3D` generous: latch only the same held direction to avoid repeated attempts, allow opposite-direction attempts without a center reset, and let `Player3D` / `Dodge3D` own cooldown rejection.
- shared 3D movement scripts must not own local-player camera logic. The earlier `Movement3D` mixed universal flight with Cinemachine behavior, which made enemy or future network-driven ships inherit irrelevant camera dependencies. Keep flight reusable and keep camera behavior on player-only components.
- shared 3D flight must not let pitched root rotation leak into a duel-plane movement basis. An earlier `ShipFlight3D` version used the ship's full `transform.forward` for thrust, recoil, and speed evaluation, so rotating the ship off the horizontal plane silently injected world `Y` velocity and looked like gravity was turning on during turns. Keep duel-plane movement projected onto a stable world plane and explicitly zero vertical drift when this path is meant to stay planar.
- shared 3D flight must not keep planar-forward thrust enabled on the active player flight path after the design has moved to real climb/dive. The old `ShipFlight3D` projected thrust and recoil onto a world-horizontal basis and then zeroed `velocity.y`, which made pitch visuals look responsive while actual travel stayed trapped on the old duel plane. If the 3D mode is meant to support real ascent and descent, thrust/recoil must use full forward and the world-Y lock must stay off on the active prefab.
- shared 3D flight must not keep passive local drift damping/alignment active when forward friction has been tuned to zero for inertial coasting. `ShipFlight3D` converts world velocity into the ship's current local frame each step, so if the ship turns during a coast, old momentum starts reading like local `x/y` drift and the assist code trims or re-aims it. When designers set `frictionDeceleration = 0`, also skip passive linear assist so world-space momentum stays intact; otherwise re-thrusting can appear to add small up/down/left/right nudges that are really hidden drift cleanup.
- shared 3D turn feel must not rely on post-physics reactions alone. The earlier combination of direct angular-velocity assignment, reactive-only mesh banking, and a camera that only changed FOV/distance made the ship feel late and disconnected even when the model visibly tilted. Keep steering assist, intent-driven visual tilt, and turn-biased camera framing coordinated as one package.
- slow-turning 3D enemy brains must not throttle target-facing updates to the same coarse think cadence used for target selection. `TankEnemyBrain3D` was only refreshing its desired heading every `thinkInterval`, so the flight motor kept rotating toward a staircase of stale target directions and the hull visibly jittered during turns. Keep expensive target acquisition throttled if needed, but update steering/facing continuously against the currently tracked target each frame.
- local-player 3D anchor states must suppress the effective thrust signal, not just the acceleration application. If Anchor only blocks velocity gain while `ShipFlight3D` still reports raw thrust input as active, thruster VFX and any other thrust-driven presentation keep firing and falsely imply the ship is accelerating.
- local-player 3D KBM free-look must not depend on an unlocked mouse cursor or on stick-style action values alone. In the 3D duel camera path, that caps rotation when the pointer hits the screen edge and can leave the mouse acting like a UI cursor instead of a relative-look device. Keep KBM free-look reading locked mouse delta through `PlayerInput3D`, and only apply that cursor lock while the active control scheme is `key+mouse`.
- local-owner 3D network prefabs must re-assert owner presentation/input wiring when ownership changes or when replicated spawn timing leaves owner input disabled. In the movement-only 3D net path, `ShipFlight3D` runs in external-simulation mode, so if the local owner never re-enables `PlayerInput3D`/`PlayerInput` after spawn, thrust/look stay zero and the ship appears fully unresponsive even though components exist on the prefab. Keep an explicit owner-control recovery hook (`OnGainedOwnership`/`EnsureOwnerLocalControlReady`) and fail loudly when owner movement is running without `PlayerInput3D`.
- local-owner 3D network prefabs must bind the active scene `CinemachineCamera` into `PlayerCameraRig3D`, not only assign the camera's tracking target once. Spawned player prefabs cannot serialize a scene camera reference, so the rig can stay disconnected and stop driving follow offset/FOV even while the camera still follows the player. Resolve one active scene Cinemachine camera during owner presentation, pass it to the rig, then bind the same camera's tracking target.
- 3D scene camera/light objects must stay grouped under the `camera/light` parent with their main-branch local offsets. Unparenting the `CinemachineCamera`, `Main Camera`, post volume, or directional light preserves similar-looking world positions in edit mode but destroys the local coordinate frame that the follow rig was authored around, making the player appear laterally/off-axis from the chase camera even though the camera still tracks.
- shared 3D arena boundary corrections must update network movement simulation state, not only the live `Rigidbody` or transform. A player can leave a shrinking arena through teleport or high-speed tunneling, and a one-frame transform clamp is overwritten by `NetMovement3D` prediction/reconciliation if `_ownerState` / `_serverState` still hold the old outside position. Route boundary clamps through `NetMovement3D.ApplyBoundaryCorrection(...)` so corrected position and velocity become the movement truth.

## Aiming, Projectiles, And Beams

- networked 3D owner combat input must stay suppressed when `NetCombat3D` is missing. The movement-only network phase deliberately blocked combat input because otherwise local projectiles could appear to work while never reaching the server or the other client. Only remove suppression once the prefab has a real combat broker.
- networked 3D owner combat input must re-check the suppression flag after spawn/ownership recovery, not only whether input components are enabled. A client owner can keep moving while `_combatInputSuppressed` remains true, which makes the ship look networked but blocks fire and abilities. Keep `NetMovement3D.EnsureOwnerLocalControlReady()` validating combat suppression against the presence of `NetCombat3D`, and let `NetCombat3D.OnNetworkSpawn()` re-run owner presentation setup once the broker exists.
- networked 3D cosmetic projectile RPCs must fail loudly when a proxy cannot resolve its local weapon/prefab binding. Host fire can work from server-authoritative components while the remote client silently drops the visual RPC if its proxy has no primary weapon fallback or missing projectile prefab reference. Keep `NetCombat3D` resolving primary projectile data from `Entity3D.PrimaryWeapon` first and `GetComponent<ProjectileWeapon3D>()` as a fallback, and keep one-shot warnings around missing cosmetic bindings.
- shared 3D duel projectiles must not reject `Player1` / `Player2` tag targets only because both ships resolve to `PlayerTeam`. Faction ally checks are correct for explicit PvE faction targeting, but in duel mode the network broker intentionally converts neutral projectile requests into opponent tags. Only apply ally rejection when `TargetFaction` is non-neutral, then let neutral duel projectiles use tag matching.
- shared 3D beam docs and implementation must stay aligned on aim source. The beam was documented as center-screen aimed while the runtime still used shooter `transform.forward`, which diverges once the chase camera and ship facing are not identical. Keep beam aim sourced from the same camera-centered path as projectile weapons when an aim camera is available.
- shared 3D enemy hardpoint beams must not blindly trust a resolved aim vector that falls behind the muzzle. Artillery-style enemies can reuse the same center-screen/network aim plumbing as player beams, but if that resolved vector crosses into the rear hemisphere the line-renderer beam can appear to snap, jitter, or fire backward even though the ship is meant to shoot only forward. Keep backward-kiting movement separate from beam aim, and enable `LaserBeam3D`'s forward-only aim clamp on enemy beam prefabs that should never fire behind their forward reference.
- 3D artillery beam visuals must not update only on the enemy AI think cadence. `ArtilleryBeamEnemyBrain3D` uses a coarse think interval for steering/fire decisions, which is fine for behavior selection but too slow for a continuous beam line. If active beam aim is only refreshed during `Think()`, the Forge line-renderer beam visibly lags, chatters during hit/miss edge cases, and feels out of sync with the rest of the scene. Keep start/stop decisions on the think loop, but refresh active beam aim every frame while the beam is firing.
- shared 3D long-range beams should not render every exact endpoint hop literally in perspective space. A tiny aim change at the muzzle becomes a large world-space move at the far tip, so medium/long-range beams can look jittery even when the underlying aim is technically correct. Keep gameplay casts exact, but smooth the rendered endpoint/direction slightly and prefer beam-facing impact orientation over per-frame collider-normal snapping when readability matters more than literal contact orientation.
- Forge enemy beam visuals must not treat impact child effects as generic always-on beam children. The first Forge integration toggled and played every child renderer/particle system when the beam started, which woke the impact effect even when the ray was not hitting anything and produced brief duplicate hit flashes. Keep impact visuals on their own hit-only toggle path, separate from the beam body and muzzle startup path.
- AI beam enemies must not retry beam startup with only a sliver of remaining energy. Without a minimum-start-energy threshold, an artillery enemy that just depleted its beam can keep requesting restarts every decision tick, which reads as hard visual jitter and fake firing. Gate startup on a configured remaining-energy minimum so the weapon has to meaningfully recharge before it can sustain the beam again.
- the artillery beam restart gate must not treat `remainingEnergy <= 0` as permission to fire. An inverted empty-energy check makes the beam appear to "machine-gun restart" exactly when the battery is fully drained, which reads as severe visual jitter and makes the energy rules feel fake. Empty beam energy must fail the restart gate.
- Forge beam-prefab tuning must stay aligned with gameplay beam width. The copied enemy Forge prefab had a much wider line (`widthMultiplier` and curve) plus an overly forgiving beam cast width, so the visual beam could look like a huge sweeping ribbon while authoritative damage still depended on a different effective centerline. Keep the line width close to the authored Forge default and keep the active beam runtime's hit radius in the same ballpark as the visible beam thickness.
- Enemy Forge beams must not split their gameplay hit ray from a second visual-impact interpretation layer once the effect needs precise contact read. The earlier `LaserBeam3D + ForgeBeamVisualDriver3D` approach let the beam line, the impact flare, and the authoritative damage endpoint evolve semi-independently, which showed up in play as wrong hit flares, grazing hits that looked centered, and general beam jitter. For enemy Forge artillery beams, use a unified runtime (`ForgeEnemyBeam3D`) that computes one hit and drives both damage and visuals from that same result.
- Forge enemy beam prefabs should not rebuild the beam root position from the current aim vector each frame or reorient the impact flare to every surface normal when mimicking the original plasma beam. The stock Forge beam is stable because it raycasts from one hardpoint transform and only moves the beam length/end position; rebuilding the world origin from aim plus normal-snapping the impact effect adds extra motion that shows up as medium-range wobble and noisy impact jitter. Keep the beam attached to the muzzle/anchor transform, and let gameplay forgiveness live in the unified beam runtime's own `hitscanRadius`.
- enemy 3D flight motors must not ignore `Entity3D` weapon/ability rotation multipliers. After enemy movement was split out of `ShipFlight3D`, the artillery enemy could keep honoring beam fire state while rotating at raw motor speed, which made the beam weapon's configured `rotationMultiplier` effectively meaningless and amplified endpoint jitter by letting the nose sweep faster than intended. Multiply enemy turn speed by the owner's combined rotation multiplier just like the player-side movement model does.
- AI beam enemies should not be able to cancel their beam for one frame, rotate at full speed, and then immediately re-fire. If the beam turn penalty only exists while the beam object is actively firing, the enemy can effectively bypass the intended artillery sluggishness by stutter-toggling the beam around aim/LOS thresholds. Keep a short post-fire rotation-penalty linger on the beam weapon so turn speed recovers gradually instead of instantly.
- shared 3D projectiles must not trust a tilted visual muzzle's forward vector for player aiming. Once banking/pitching is applied to the visual model, muzzle children can tilt away from the real gameplay aim. Resolve player projectile direction from camera aim or another authoritative target point, then spawn from the muzzle position using that direction.
- shared 3D center-screen projectiles must not rely on muzzle-to-center-point convergence alone once the camera is allowed to lag and frame the ship off-center. That path is mathematically valid but can look like shots are missing the reticle during hard turns because the muzzle starts far from the center ray. Keep a tunable blend back toward the raw center-screen aim direction so off-center chase framing still reads as center aiming.
- shared 3D projectiles must not carry redundant physics components when the hit path is already explicit hitscan/sweep logic. The earlier 3D projectile version kept a projectile collider even though collision results were being decided by scripted casts. That added avoidable component cost and blurred the true ownership of hit detection. Keep the projectile prefab visual-only unless a real gameplay requirement needs its own physics body.
- shared 3D hold abilities such as beam weapons must not inherit tap-ability cooldown gating from `Ability3D.TryUseAbility(...)`. That base path timestamps the press event, which is fine for tap abilities but wrong for hold/release weapons and can look like the beam randomly expires or has a fake regen delay before it can fire again.
- shared 3D beam capacity is an overheat meter, not remaining fuel. If `drainRate <= 0` or `capacity <= 0`, the 3D beam should be treated as non-draining and the HUD/resource gate should stay inactive instead of accumulating invisible heat.
- shared 3D reflect shields cannot rely on `OnTriggerEnter`-style callbacks from the projectile itself when the projectile path is explicit sweep logic. `Projectile3D` decides hits by spherecasting and may not carry a live collision body, so the reflect path has to be checked from `Projectile3D.ProcessHit(...)` before normal damage/despawn logic runs.
- shared 3D reflect shields must not treat reflection as a simple `-direction` flip when the gameplay goal is "send the shot back to who fired it." In full 3D space the attacker can sit above, below, or offset from the incoming path, so a planar reversal can miss even though the parry looked correct. Resolve the reflected heading from the projectile position to the original shooter when that shooter still exists, and only fall back to a raw reverse vector if that ownership context is gone.
- shared 3D charged projectiles must not assume every tier prefab shares the same pivot length. Charge-shot tiers can swap between very short and very long projectile meshes, and some prefabs use a midpoint pivot. If every tier uses the same spawn distance, long shots can spawn back through the ship even though short ones look correct. Keep per-tier forward spawn compensation exposed in the ability config when the projectile art varies by tier.
- shared 3D primary-weapon overheat must not be tracked separately by the weapon gate and the HUD reticle. If `ProjectileWeapon3D` enforces one heat value while `PlayerAimReticle3D` animates a different local approximation, the player gets false feedback about why base fire stopped and future tuning becomes misleading. Keep the overheat state authoritative on `Entity3D`, spend it from the real base-weapon fire path, and have the reticle read that same normalized value for bracket fill.
- shared 3D beam visuals must not use `SphereCast` entry distance as the rendered beam length when the hit effect is placed at `hit.point`. With a forgiving beam radius, `RaycastHit.distance` reports when the cast sphere first touches the target, which makes the visible beam stop short by roughly the cast radius even though damage and impact VFX land correctly. When the beam should visually reach the displayed impact point, derive the rendered length from the hit point projected onto the beam direction instead of the raw cast-entry distance.
- networked 3D beams and tractor beams must not resolve screen-center aim from a local `aimCamera` on any peer except the owning client. `Weapon3D.Awake` caches `Camera.main`, and `NetMovement3D.SetWeaponAimCamera` only rebinds it for the local owner. That leaves the server-authoritative copy on the host and the cosmetic proxy on the opposite client both sampling the viewer's own camera for `ViewportPointToRay`, so the non-host's laser never actually hits the target ship and the remote proxy's visuals point in whatever direction the viewer happens to face. Replicate the owner-computed aim direction on beam/tractor toggle plus per-tick aim-update RPCs and consume that replicated direction on every non-owner peer through `LaserBeam3D.SetNetworkAim(...)` / `TractorBeam3D.ApplyNetworkTractorBeamAim(...)`.
- networked 3D beam owners must not feed their own live aim resolver from cached replicated aim state. `ConvergeBeamWeapon3D` cached the initial aim in `_pendingNetworkAimDirection` and then let owner-side `ResolveOwnerAimDirection()` read that cache, so the owner kept sending the first aim direction every tick while held. Match `BeamWeapon3D`: owners always resolve live camera aim, while only server/remote non-owner copies consume the replicated aim cache.
- shared 3D projectile requests that provide a `spawnAnchor` must not silently fall back to the base weapon's full muzzle array when `request.muzzles` is empty. `FireProjectilePattern(...)` fires once per resolved muzzle entry, and `ResolveProjectileSpawnPosition(...)` uses the same `spawnAnchor` each pass, so a single-anchor ability shot can duplicate into 4 stacked projectiles if the base weapon config has 4 muzzles. When a request uses `spawnAnchor` and no explicit muzzle list, resolve exactly one firing source from that anchor.
- networked 3D beam replication must not be hardcoded to `BeamWeapon3D`. Class 4's converge beam lives on a different `Weapon3D` subtype, so a broker that only does `GetComponent<BeamWeapon3D>()` makes owner fire look correct locally while server/remote copies never receive start, stop, or aim updates. Route beam RPC state through a shared beam-network interface and let each beam weapon implement that contract.
- networked 3D dodge movement must not be implemented as only a local Rigidbody slide or a one-frame combat velocity delta. `NetMovement3D` and `MovementSimulation3D` rebuild movement every tick from authoritative state, so a dodge that only writes velocity once can "activate" while producing no real displacement because the next simulation step overwrites it. Send dodge as replayable `NetInputSnapshot3D` data, then store it as persistent movement state that the simulation honors for the full slide duration.
- local 3D dodge fallback must not route into `NetMovement3D` just because that component exists on a prefab. In standalone or scene-test play, an unspawned `NetMovement3D` does not run the network movement tick, so dodge audio/cooldown can fire while no slide is consumed. Only use the network dodge path when `NetTickUtil` is active and the movement object is spawned; otherwise use the local Rigidbody slide fallback.
- shared 3D dodge movement should be additive displacement, not a temporary velocity takeover. If dodge zeros or replaces the ship's normal velocity/thrust state, flight telemetry consumers such as thrusters, trails, tilt, and camera effects see a fake stop followed by a fake restart. Keep normal flight simulation running and layer the dodge slide on top as extra position movement for the slide duration.
- shared 3D dodge displacement must respect blocking arena bounds before moving the Rigidbody. If additive dodge pushes into a generated blocker or outside a hard boundary, physics/correction pushes back while the remaining dodge frames push forward again, causing turbo jitter. Clamp local dodge steps and network dodge offsets through `ArenaBoundary3D.ClampPositionInside(...)` when `BlocksMovement` is enabled.
- networked 3D dodge must not let the owning client apply unacknowledged local movement outside the replayable movement input stream. If the owner starts dodge movement locally and the server applies the authoritative dodge later via combat RPC, reconciliation snaps the owner back to pre-dodge server states and produces severe jitter. Keep immediate owner feedback presentation-only unless dodge is encoded into predicted inputs and replayed by `NetMovement3D`.
- shared 3D guided missiles must not reuse a 2D `transform.up` or planar-turning homing path. Class 4 missiles need to climb, dive, and reacquire targets in full 3D space, otherwise the projectile looks correct only when both ships stay near the old duel plane and breaks as soon as vertical separation matters. Keep missile steering in a true 3D direction basis and reacquire through the replicated duel target/faction path.
- networked reflected 3D projectiles must preserve projectile-specific scale overrides, not just speed/damage/lifetime. Class 4 empowered missiles enlarge through the projectile request, so if the reflected-projectile RPC only rebroadcasts kinematic values, remote clients spawn the reflected missile at the wrong size even though the server damage is correct. Carry the applied projectile scale multiplier through the reflected-projectile replication payload as well.
- player-owned 3D projectile weapons must not hardcode generic `"Enemy"` tags or `EnemyTeam` targeting when the same weapon can be used in both duels and Invasion. That makes the projectile fly normally but silently reject the opposing player as a valid damage/shield target in duel scenes because both players live on `PlayerTeam` and use `Player1` / `Player2` tags. Normalize generic player-fired projectile requests at fire time: prefer `EnemyTeam` when real enemies are present, otherwise resolve the duel opponent tag explicitly.

## Ability Integration

- shared teleport abilities reused from the 2D path must not keep `transform.up` movement, `z` pinning, or `Collider2D`-only disable/restore logic once they are placed on 3D ships. That combination makes the ship blink but still teleport in the old 2D axis basis, leaves 3D colliders active during the warp, and can restore the wrong post-teleport scale if the mesh prefab is authored with non-unit local scale. Resolve teleport travel from the ship's planar 3D forward, preserve the 3D flight-plane axis, and cache/restore both 2D and 3D presentation state.
- shared 3D teleport pulsewave VFX must not keep a fixed world rotation when the gameplay camera follows ship heading. A flat pulse mesh that spawns with a static rotation can look correct from one heading and edge-on or skewed from another. Billboard teleport pulsewaves to the active gameplay camera, and preserve any mesh-authoring axis offset the prefab needs, so departure and arrival reads stay consistent regardless of ship facing.
- shared 3D teleport one-shot audio must not reuse a player-level `AudioSource` that may already be configured for looping beam, shield, or other sustained effects. `SoundEffect.Play(...)` uses the source's current loop state, so a reused looping source makes teleport exit/arrival sounds loop even though the ability only triggers them once. Keep teleport on its own dedicated non-looping `AudioSource` so one-shot playback cannot inherit stale loop settings from another 3D system.
- shared 3D ability hooks must be consumed by the movement and firing drivers, not just exposed on `Ability3D`. Before the charged-shot path was integrated, the 3D runtime defined thrust multipliers, rotation multipliers, and primary-fire locks, but `ShipFlight3D`, `PlayerInput3D`, and the enemy fire loop never read them. That made charge penalties and fire suppression look configured in the ability while doing nothing in play. Keep the runtime querying `Entity3D` for combined ability state whenever a new 3D ability relies on those hooks.
- shared 3D cooldown attacks must not stay wired as `Ability3D` components after the runtime has moved to 3 weapon slots plus 2 ability slots. Leaving cooldown attacks on the ability path makes them invisible to weapon selection, shared fire input, and weapon cooldown HUD state even though they still spawn projectiles. When a combat action is meant to be one of the selectable weapons, port it to `Weapon3D`, put it in the entity weapon array, and mark its availability mode to match its real gating model.
- shared 3D tractor-beam pulls must not reuse planar cone math from the 2.5D path. A planar projection (`ProjectOnPlane`) plus `velocity.y = 0` can make the VFX look active while targets only move on a flat slice and never get true vertical pull. Keep cone-angle tests and pull velocity in full 3D vectors, and treat beam activation/deactivation as explicit state so the visual cannot remain stuck active after timing edge cases.
- shared 3D tractor-beam volume meshes must not default to an opaque or high-alpha end cap when viewed from a chase camera. Closing the cone tip can read like a giant flat screen-space card even when the pull logic is fully 3D. Keep the end cap optional (or very low alpha) so the effect reads as depth volume instead of a billboard.
- shared 3D tractor-beam suction particles must not combine stretch-render mode, trails, and strong noise when the camera sits near the beam axis. That stack can produce intermittent screen-side streak artifacts that look like rendering glitches rather than pull motion. Keep suction particles on deterministic inward velocity (billboard render, no trails/noise outliers) when readability is the priority.
- shared 3D tractor-beam visuals must not be procedurally authored in `TractorBeam3D` when the desired result needs art-directed cone layering and ring spacing. The earlier runtime mesh/material/particle setup technically produced a beam, but it locked the look to code-only parameters and made iteration worse than building the effect directly in the prefab. Keep `TractorBeam3D` responsible for pull logic and activation only, and author the beam cone/rings as a manual child hierarchy referenced through `visualRoot`.
- shared 3D tractor-beam cone aim must not be resolved from a pitched visual spawn transform's `forward` when the gameplay intent is center-screen targeting. The previous `TractorBeam3D` path used `spawnPoint.forward` for cone checks, so a slightly up-tilted ship mesh made the pull volume drift above the reticle and feel detached from projectile/beam aim. Resolve tractor-beam direction from the same center-screen camera ray pattern used by weapons, and keep `spawnPoint` ownership limited to beam origin/visual placement.
- shared 3D tractor-beam visuals must not stay in a static authored rotation once cone aim is camera-driven. A static `visualRoot` can keep pointing upward while pull checks use center-screen direction, which makes the effect look broken even if gameplay is correct. Drive `visualRoot` transform from the resolved gameplay cone direction (with a small configurable rotation offset only for mesh-axis compensation), and use a Scene gizmo to validate cone size/alignment during prefab tuning.

## VFX, Feedback, And Presentation

- shared 3D visual controllers must not allocate Unity engine wrapper objects such as `MaterialPropertyBlock` in MonoBehaviour field initializers. Unity can construct scripts during serialization/import, where `CreateImpl` is not allowed, which makes prefabs fail to import and can cascade into null `GetPropertyBlock(...)` errors. For prefab-centered VFX that only need shared pulse values, prefer separate material assets for per-renderer constants and write pulse values to the assigned material; use property blocks only from runtime methods that are known not to run during import/preview construction.
- screen-space black-hole lensing must not assume transparent/additive disk pixels are automatically available in `_CameraOpaqueTexture`. URP copies opaque color before normal transparent rendering, so a standard transparent accretion disk will render directly but will not appear in the bent Einstein-ring sample. Keep lensable disk materials in an opaque render-queue range, or add a dedicated render feature that copies color after the disk and before the singularity lensing pass.
- screen-space black-hole lensing must not blindly use every bent `_CameraOpaqueTexture` sample as physical background. If the bent UV lands on a foreground ship, asteroid, or world cursor, the lens appears to smear nearby gameplay objects into the black hole even when they are not behind it. Prefer `BlackHoleLensSourceRendererFeature` and a dedicated lens-source layer mask so only intentionally lensable renderers are captured; depth rejection is only a fallback, because large gameplay scale can make foreground objects look numerically close to far background depth.
- black-hole lensing shells must not render as late transparent overlays. A `Transparent+` queue can still cover ship flames, world reticles, and other transparent gameplay readability VFX even when the lens source texture correctly excludes those objects. Keep the singularity material in an early transparent queue, currently 2900 / `Transparent-100`, and let normal gameplay transparent materials render afterward.
- background star particles must not share the same normal transparent queue as gameplay VFX when a screen-space black hole needs to occlude them. Sorting Priority is not enough if the material still renders after the singularity shell; keep background-only star particles earlier than the lensing shell, currently queue 2800 / `Transparent-200`.
- screen-space lens UVs must not be saturated before sampling. Clamping an off-screen bent UV to `0` or `1` can pin a bright disk or photon-ring pixel to the edge of the lens, which shows up as small white flashes while the camera pans. Fade invalid UVs out and use an explicit off-screen arc fallback if the disk should remain readable beyond the camera frame.
- dedicated black-hole lens-source sampling only contains what the camera captured. If the accretion disk is off-screen, there is no real disk pixel to bend; use the singularity shader's off-screen fallback arc for continuity rather than expecting final-frame sampling to recover invisible source pixels.
- the singularity shader's event-horizon interior must early-return before any scene-color, lensed-source, photon, or procedural arc work. Applying black only at the end makes rare sampled-color instability hard to diagnose and can allow intermittent bright blobs inside the shadow; use `Debug View Mode` on the material to inspect horizon/lens masks when this regresses.
- prefer `Starfall/3D/BlackHole/SingularitySimple` for gameplay-background black holes when screen-space lensing artifacts are more distracting than useful. The simple shader deliberately avoids scene/depth/lens-source sampling and relies on a black core, photon ring, subtle procedural arc, and the real accretion disk for the readable black-hole silhouette.
- the black-hole accretion disk must explicitly mask out the event-horizon shadow area instead of relying on the transparent singularity shell to cover it later. The disk renders in an opaque/capture queue and writes depth so URP can lens it, which means bright inner disk lanes can sometimes win depth and bloom as circular white blobs inside the black core unless the disk shader clips that center region itself.
- lensable black-hole disk shaders must not render in the opaque queue with `ZWrite Off`. URP draws the skybox after opaque geometry, so the skybox overwrites any early additive disk pixels that did not write depth, leaving the disk visible only over asteroids/ships that already filled the depth buffer. Keep depth writes on for the lens-capture disk and use alpha clipping to avoid writing depth for fully faded corners.
- pure radial screen-space lensing can undersell the upper/lower accretion arcs when the inward sample lands on the disk's central hole instead of a bright ring lane. Keep the singularity shader's lensed disk arc controls available as a procedural, lane-based assist so the reference-style disk bridge remains readable without turning into a soft glow smear.
- lensed accretion arcs must animate their lane phase, not only their noise lookup. If the radial lane sine uses only screen radius, the arc can look like a separate static decal even when small noise wisps move. Drive the lensed arc from the same spin/infall/spiral terms as the flat disk material.
- black-hole singularity shaders must not derive their screen-space radius by projecting local axis-offset points and subtracting the projected center. In perspective cameras, that makes the lens/core radius grow as the black hole moves off-center because the sampled offsets use different clip-space depths. Compute the shader radius from scaled world radius, camera-to-object distance, and projection focal length so camera yaw does not make the background black hole swell at screen edges.
- quad-authored black-hole accretion disks must not derive circular swirl coordinates from local mesh position unless the mesh dimensions and pivot are intentionally controlled. A default quad's useful authoring contract is its UV square, so convert `uv * 2 - 1` into polar radius/angle in the shader and use the radius to mask the corners into a visual circle.
- white dwarf compact lensing must not be enabled on a URP renderer that has opaque texture disabled. The star core/corona will still render, but the lensing shell samples `_CameraOpaqueTexture`, so a renderer without that copy produces missing or misleading shimmer. Use `PC_RPAsset.asset` or another opaque-texture-enabled renderer when turning on `LensingShell`.
- HDR white dwarf materials do not create bloom by themselves. If the active camera has post-processing disabled, or the active volume Bloom intensity is zero, the star will look like a bright mesh without the intended glare. Verify camera post-processing and volume Bloom before retuning shader brightness.
- networked 3D round-flow presentation must not assume `NetworkSessionData.Instance` is available during the scene manager's first `Start` frame on every peer. Client scene load, Netcode object spawn, and persistent session-object timing can arrive in a different order, which leaves round-end/game-end RPC events firing with no 3D listener attached. Keep `SceneManager3D` resilient by delaying network-mode resolution briefly and retrying event subscription while the network session is active.
- shared 3D force-field walls must not rely on the Forge3D collision callbacks alone for arena containment or proximity reveal. Collision callbacks do not handle "near the wall" warning, shrink-wide visibility, teleport escapes, or network authority. Keep gameplay blocking on dedicated colliders plus `ArenaBoundary3D`, and drive force-field visibility cosmetically through shader property blocks.
- shared 3D force-field wall colliders must not be sized in world units on the same transform that is already scaled to the wall dimensions. A quad scaled to 1000x1000 with a `BoxCollider.size` also set to 1000x1000 creates an enormous world collider that can overlap ships near the arena center and cause violent physics jitter. When the blocker shares the visual transform, keep collider `size` near 1x1 and let transform scale provide the dimensions.
- shared 3D force-field wall setup must not reset the renderer or blocker transform to local origin when those components live on the same object as `ForceFieldBoundaryWall3D`. The boundary first places the wall object at a cube face; setting `renderer.transform.localPosition = Vector3.zero` afterward moves that same object back to the boundary parent's origin, stacking every wall on the player. Only zero child renderer/blocker transforms when they are actually child objects.
- shared 3D force-field proximity hits must be sent to the rendered mesh plane, not to the inner face of the wall collider thickness. Forge3D converts world hit points into the mesh's local space and compares them to object-space vertices; offsetting the point along the wall normal can put the impact mask off the visible quad, especially when the quad is scaled to arena size.
- shared 3D force-field wall visuals should not stretch a default unit quad to arena size when Forge3D hit masks need readable physical scale. The shader compares impact points against object-space vertex positions, so transform-scaling a 1-unit quad to 1000 units makes a small local-space hit become a huge world-space bloom. Build the wall mesh at real dimensions with transform scale 1, then tile UVs through `Texture World Size`.
- shared 3D force-field proximity reveal must not use `_Static` on one full-wall renderer for normal approach warnings unless the design intentionally wants the entire wall visible. `_Static` is a renderer/material visibility term, so proximity needs generated visual segments if only nearby wall panels should light up; reserve full-wall `_Static` for shrink warnings or deliberate full-wall visibility.
- shared 3D hex arena visuals should not require hundreds of small wall quads just to make individual hex regions appear near the player. That object-heavy approach creates avoidable renderer count, material-property churn, and prefab authoring complexity for a PS4-targeted path. Keep the current boundary as one generated inward-facing box mesh and let `Starfall/3D/ProceduralHexArenaBoundary` sample a tileable hex mask texture per fragment, while the gameplay boundary is owned separately by soft-zone damage or explicitly enabled blocker colliders.
- shared 3D hex mask shaders should not use texture alpha as the default visibility channel when the source texture is imported as a Unity sprite. Sprite imports often have alpha set to 1 across the full image, so `max(rgb, alpha)` turns the entire wall visible and makes the mask look ignored. Sample RGB brightness for the mask unless an intentionally authored alpha mask is required.
- shared 3D arena hex textures must be imported with repeat tiling for large generated walls. If the texture keeps `Wrap Mode = Clamp`, world-space UVs outside the first tile smear the texture edge across the arena and can look like the material assignment failed.
- shared 3D arena proximity reveal should not use one radius for both "when the player starts seeing the barrier" and "how much wall is visible." Coupling those values means designers cannot give early warning without revealing a huge wall patch at close range. Keep `Reveal Distance` as the approach trigger distance and `Visible Patch Radius` as the surface footprint around the nearest barrier point.
- shared 3D arena proximity reveal should not choose one winning wall when multiple faces may be relevant. Nearest-surface reveal pops when a different face becomes slightly closer, while forward-only reveal feels like a spotlight rather than an arena boundary warning. Generate independent reveal samples for every arena face within `Reveal Distance` so adjacent walls fade smoothly and the surface footprint stays controlled by `Visible Patch Radius`.
- shared 3D arena outside warnings should not depend on the normal proximity reveal once a player has already crossed the boundary. If the visible patch remains small or uses the normal reveal distance, the player can be outside the field without a clear nearby wall reference. Use an outside reveal override that targets the closest arena face with larger reveal distance and patch radius until the player returns inside.
- shared 3D arena shrink waves should not independently target width and length once the design is a shrinking cube/box percentage. Separate dimensions are harder to tune and can distort the arena over waves. Keep each wave as `Target Size Percent` plus `Duration` plus `Time Until Next Wave`, and derive width, height, and length from the starting dimensions.
- shared 3D arena shrinking should not force global wall visibility or flashing unless the design explicitly asks for a warning phase. The current boundary should shrink silently and keep visibility controlled by proximity/outside reveal only.
- shared 3D soft arena boundaries must not leave old hard-containment colliders or clamp correction active. If the design allows players to pass through the field and punishes them outside, enabled blocker colliders or network boundary correction will fight player intent and make the warning/damage state inconsistent. Keep blocker colliders disabled by default and apply outside damage from the authoritative side while publishing the arena-boundary vignette only to local HUDs.
- generated 3D arena visuals must not stay inactive just because the component has not been started by scene flow yet. If `ArenaBoundary3D.Active` is false, the visual renderer and outside-damage/vignette loop are intentionally inactive, which makes the boundary look broken during standalone testing. Keep `Start Active On Enable` enabled for standalone testing, or ensure `SceneManager3D` calls `StartBoundary()` before combat begins.
- shared 3D visual tilt must not derive recoil pitch only from total forward acceleration. In the 3D flight path, weapon recoil is injected as a velocity impulse, so folding it into the same signed acceleration term as thrust can invert the feel and removes independent tuning. Keep thrust pitch and recoil pitch as separate inputs, with recoil sensitivity exposed on `Entity3D`.
- shared 3D death presentation must not stay embedded in `Entity3D` or reuse the 2D ship-part scatter script unchanged. The old path depended on `Rigidbody2D`, planar cone math, and a fake `z` render offset, which reads wrong once the ship is a true 3D object. Keep ship death VFX in `DeathEffects3D`, keep per-fragment behavior in `ShipPartScatter3D`, and scatter with real 3D velocity and angular motion.
- shared 3D one-shot particle effects must not rely on scene unload or manual cleanup to disappear. That leaves invisible-but-alive objects in the scene and defeats pooling. Use `TimedEffectCleanup3D` so temporary VFX either despawn back into `GameObjectPool3D` or destroy themselves after their particle lifetime expires.
- shared 3D split-state lightning must not treat the shader asset itself as if it can place lightning in the world. Stopping at the shader/material step produces no controlled ship effect because nothing defines where the pixels should render. For ship seam lightning, always attach the material to a mesh-bearing `LightningBolt3D` object with explicit anchor transforms, and group those bolts under `SplitStateLightningRig3D` when the whole split-state effect should toggle together.
- shared 3D split-state lightning must not blindly reset bolt visibility in `Awake()` without respecting the renderer's authored enabled state. An earlier `LightningBolt3D` version defaulted its private visibility flag to `false` and then applied that to the `MeshRenderer` on play start, which made bolts look correct in edit mode but disappear the moment the scene began. Cache the renderer's authored enabled state before applying runtime control so preview-visible bolts remain visible unless a rig or gameplay script intentionally hides them.
- shared 3D split-state lightning must not assume every discovered `LightningBolt3D` is fully configured when a rig toggles the effect on startup. An earlier version let `SplitStateLightningRig3D` enable bolts immediately, and any bolt missing a `startPoint` or `endPoint` crashed inside `UpdateQuad()`. Guard bolt activation against missing anchors, log the setup error once, and fail closed by hiding the invalid bolt instead of throwing.
- local-player 3D charge-screen effects must not be implemented as a center-distance vignette when the desired read is energized screen edges. The vignette path biases the effect toward radial darkening/tinting and visibly contaminates the center of the frame. Use a fullscreen edge-glow pass instead.
- local-player 3D fullscreen charge effects must stay owned by one local camera path only. If multiple controllers write the same global edge-glow parameters, whichever updates last wins and the wrong camera can inherit another ship's charge state.
- local-player 3D chromatic-aberration hit feedback must not reuse the 2.5D path's `impactForce`-driven intensity calculation without rechecking the 3D damage contract. The old player script scaled the effect from impact force instead of real damage taken, but the 3D projectile and beam paths call `TakeDamage(...)` without a separate impact-force payload. In the 3D path, drive chromatic intensity from the actual shield/hull damage applied and keep the post-process controller local to the player camera runtime.
- local-player 3D Cinemachine impulse shake must not be emitted by every spawned player proxy in networked scenes. Impulse listeners are camera-side, so a remote player's speed or hit feedback can shake the local viewer if the source is allowed to fire on non-owner objects. Gate `PlayerScreenShake3D` impulses to the local network owner, and trigger hit shake only after `Player3D` confirms real damage was applied.
- local-player 3D Cinemachine impulse shake must not rely on `CinemachineImpulseSource.DefaultVelocity` when the authored prefab may have serialized it as zero. `GenerateImpulse(float)` multiplies the force by `DefaultVelocity`, so a zero vector creates an event with no movement even though the source/listener channels match. Use `GenerateImpulseWithVelocity(...)` with an explicit non-zero direction for player shake.
- local-player 3D screen shake should not use one fixed vertical/player-local impulse direction or leave screen-space HUD canvases static. That reads as the ship/world bobbing up and down instead of the camera taking impact, especially when the UI layer stays perfectly still. Randomize player shake across the gameplay camera plane and apply a small matching offset/roll to active screen-space HUD roots from the same local-owner feedback component.
- local-player 3D generated combat audio must not default runtime `AudioSource` components to 2D or leave them on logarithmic rolloff. `Player3D.InitializeAudio()` used `spatialBlend = 0f` on the pooled damage sources and beam loop, several 3D abilities plus death VFX did the same, and the shared `SoundEffect.PlayAtPoint(...)` helper also spawned a temporary source. That combination made positional ship feedback collapse into flat UI-style sound and stay audible too far away. Keep code-spawned combat audio at `spatialBlend = 1f` with `AudioRolloffMode.Linear` when the intent is world-space feedback.
- shared 3D speed trails must not be authored from the ship root or from a single center emitter when the look goal is wingtip streaking. That setup turns the effect into a flat center ribbon and breaks the silhouette read from behind. Author explicit wing source transforms and let `ShipSpeedFx3D` build the layered trail renderers from those points so the streaks stay attached to the ship's lateral silhouette.
- shared 3D speed trails must not offset the emitter itself away from the authored wing transform just to fake camera-facing softness or turbulence. World-space emitter drift makes the trail read like it is detached from the hull during flight. Keep the emitter locked to the wing source and let the trail renderer alignment, material, width curve, and gradient sell the softness instead.
- networked 3D speed FX must not rely on NGO to hide local boost presentation automatically. `ShipSpeedFx3D` is a plain `MonoBehaviour`, so every spawned replica can still build dust/trail visuals unless the script checks ownership itself. Keep speed FX owner-only in active network sessions so remote ships do not show another player's boost trails.
- shared 3D split-state piece offsets must be applied as `authored local position + configured offset`, not as an overwrite of the current transform or as repeated incremental pushes. Otherwise the effect either destroys prefab-authored asymmetry or accumulates drift every time the split state toggles.

## Environment And Screen-Space Effects

- 3D arena boundary gizmos should not be hidden behind a separate "only when selected" toggle when the boundary is used for scene-scale tuning. `OnDrawGizmosSelected` only helps after the object is selected, so designers can miss the active play volume while adjusting cameras, spawns, or encounter layout. Keep `ArenaBoundary3D` drawing from `OnDrawGizmos` and use the main `drawBoundaryGizmos` toggle as the explicit opt-out.
- 3D black hole lensing should not be described as sampling the final frame when it uses URP `_CameraOpaqueTexture`. In Unity 6 / URP 17 this texture is copied after the skybox, which is enough for starfield skybox lensing, but it excludes transparent VFX drawn later. Keep opaque texture enabled on the active renderer asset for the current black hole prefab; add a dedicated late scene-color copy only if the effect must bend transparent objects behind it.
- 3D distant-background parallax for world objects should follow translation only, not camera rotation. A camera-local lock can make far planets rotate around the camera and disappear whenever the player looks around, while raw camera deltas can inherit chase-camera orbit/lag. Prefer an explicit player/ship parallax origin and move the background object by a small fraction of that origin's world translation.
- large distant 3D set pieces should not rely on raw perspective projection if they are meant to read like fixed background celestial objects. At a constant world distance, turning the perspective camera can reduce camera-forward depth and make the object swell near screen edges. Use `DistantAngularSizeStabilizer3D` for visual-only background objects that need stable apparent size while the player yaws.

## HUD And Player-Facing Readability

- 3D Invasion spawn-arrival enemies must not be counted or surfaced by HUD discovery before their reveal actually finishes. The old path tracked them in `InvasionWaveManager3D` at instantiate time while `SpawnArrivalEffect3D` merely hid renderers and disabled gameplay, so the enemy counter and target-awareness indicator showed ships that had not visibly entered play yet. Keep unrevealed arrivals in a pending state, exclude them from target discovery, and only promote them into alive-enemy/HUD tracking once the arrival effect reports reveal completion.
- local-player 3D HUD managers in network scenes must not keep an explicit scene-player reference with auto-binding disabled. Networked matches spawn runtime player objects, so a scene-authored player reference can leave health/shield text listening to the wrong object while real combat state updates elsewhere. Keep scene HUD managers auto-bound to the local player and retry binding briefly after spawn/ownership setup.
- local-player 3D low-health vignette HUD effects must bind through `PlayerHUDManager3D` instead of ship-prefab-local assumptions. Scene HUD canvases exist outside player prefabs, so ship-local setup can leave the vignette listening to the wrong player or no player in networked spawn order. Keep low-health vignette scripts as `PlayerHUDBindingTarget3D` components with an explicit HUD-manager reference when needed.
- player-prefab 3D effects must not hold direct serialized references to scene HUD `Image` objects. A prefab such as `GigablastChargeEdgeGlow3D` can appear configurable in isolation but cannot safely own a scene-only HUD object reference across scenes/network spawn flows. Route player-driven HUD visuals through `PlayerHUDManager3D` message dispatch and let HUD-side receivers own the concrete `Image` references.
- local-player 3D HUD vignette channels must not assume message producers always publish every frame forever. If a producer drops out after sending a non-zero alpha (for example a charge effect during bind/spawn transitions), the HUD can remain stuck on the last received tint, which can read as a permanent white vignette even when low-health logic is correct. Keep HUD-side channel state resilient by expiring stale channel messages and fading their contribution out automatically.
- local-player 3D aim-reticle feedback must not raycast from a different origin or camera than the actual weapon aim path. If the HUD closes brackets from `transform.forward` or a different camera while the weapon runtime fires from screen-center camera aim, the reticle can claim "enemy under aim" even though the real shot line disagrees, or stay open while shots are correctly centered. Keep hover/readability checks sourced from the same center-screen aim ray the weapon uses.
- local-player 3D reticle spin must not assume "ability button is being held" means "a shot just happened." Charged abilities can spend most of their lifetime in a held charge state where the player is not actually firing yet, while beam-style abilities really do need continuous spin the whole time they are active. Keep reticle spin sourced from actual weapon fire timestamps or explicit ability spin providers instead of raw input state alone.
- local-player 3D health/shield HUD ports must not move the 2.5D combat-state update logic into a scene manager just because the canvas is different. In the 2.5D path, `Player` owns HUD initialization plus health/shield updates, while the scene manager only supplies the correct canvas binding. Rebuilding the bars from scene-level polling or phase flow makes the HUD easier to desync from real combat state. Keep the 3D HUD as a thin local-player binder that `Player3D` updates directly from combat hooks.
- local-player 3D scene HUD elements must not assume they live on the player prefab or let every spawned player claim the shared HUD in `Awake()`. That breaks as soon as the health canvas, reticle, and spawned weapon/ability HUD live in the scene instead of under the ship, and it becomes outright wrong for future networked ownership where only one player on a peer is local. Keep one `PlayerHUDManager3D` on the HUD, let it resolve the local player, and have each HUD element subscribe to that shared binding.
- local-player 3D target-awareness HUD must not cache scene-authored enemy references or assume only `Enemy3D` objects are valid targets. In network duels the opponent is usually a remote `Player3D` proxy whose transform and combat state are replicated by `NetMovement3D` / `NetCombat3D`. Bind through `PlayerHUDManager3D`, exclude the bound local player, and read all valid non-local `Entity3D` proxies locally instead of adding target-awareness RPCs.
- local-player 3D target-awareness HUD must not treat all same-faction explicit targets as allies after the Invasion faction rollout. Duel ships now commonly carry explicit `FactionMember3D = PlayerTeam` for shared prefab compatibility, so a pure same-faction rejection makes the remote `Player3D` opponent disappear from discovery entirely and leaves offscreen indicators permanently inactive. Keep PvE ally filtering, but preserve `Player1` versus `Player2` duel-opponent detection when deciding whether a same-faction player should still be tracked.
- local-player 3D target-awareness HUD must not discover every alive `Entity3D` in the scene and only sort it out later at presentation time. In 3D Invasion that makes the tracker light up distant enemies across the whole map and can also pull in non-hostile entities before faction checks happen. Filter discovery by the HUD's serialized hostile faction and a tunable awareness range so only nearby intended enemies get widgets.
- local-player 3D target-awareness HUD must not preserve `Player1`/`Player2` duel hostility in co-op scenes just because the fallback exists for duel compatibility. Invasion teammates are still player-tagged ships, so an unconditional duel-opponent fallback will mark the other player as hostile even when both ships are correctly authored as `PlayerTeam`. Only allow the duel tag fallback in duel-shaped scenes; disable it when `InvasionSceneManager3D` owns the scene.
- local-player 3D target-awareness widget templates may be inactive, but the runtime widget container and projection canvas/root must be active. If the inactive template is also assigned as the widget container or canvas root, cloned indicators remain inactive through their parent even when the script finds valid targets. Keep the authored template separate from the active parent, or let `TargetAwarenessHUD3D` fall back to the template's active parent.
- local-player 3D target-awareness indicators should not rotate while the target is visibly on screen. Directional rotation is useful for offscreen or occluded targets, but a visible far target that keeps recalculating direction from tiny screen-space movement can look like wild spinning. Keep visible floating indicators upright and reserve rotation for directional guidance states.
- local-player 3D target-awareness brackets should not reuse an occlusion/aim probe offset as their UI projection anchor. A body-height raycast point can be correct for line-of-sight checks while visibly centering brackets above or beside the ship. Keep the UI projection offset separate from the occlusion probe offset so authored brackets can sit on the visual center.
- local-player 3D target-awareness floating indicators should not reuse a bracket/body offset if the intended read is "the enemy is exactly here." Keep the floating indicator projection offset separate from bracket and occlusion offsets so the arrow can sit directly over the ship while brackets/bars can still use their own authored anchor.
- local-player 3D target-awareness edge clamps may need asymmetric top/bottom padding. Perspective camera framing, cockpit composition, and authored HUD layout can leave less usable space at the top than the bottom, so do not force one vertical padding value if the top indicator needs to sit lower.
- local-player 3D target-awareness brackets and health/shield bars must not be scaled and positioned from independent distance-only values. That made small, medium, and large enemies read inconsistently because the UI ignored the actual projected silhouette while the bars kept a fixed relationship to the widget instead of the bracket edge. Size brackets from projected active mesh/skinned renderer bounds or an authored `TargetAwarenessBounds3D` local box, then place bars from the computed bracket edge.
- local-player 3D target-awareness attack flashes must not infer danger from weapon cooldowns or generic enemy fire state. In co-op, the same enemy may be firing at a teammate, so offscreen red brackets should pulse only when the replicated/local attack report names the bound local player as the intended target and the widget is in edge-indicator state. Pre-fire flashes should come from explicit charged-attack scheduling, not from guessing that a cooldown might fire soon.
- local-player 3D target-awareness health/shield bars must use filled images or segmented bars for their foreground value. Assigning a normal Simple `Image` and changing `fillAmount` leaves the visual unchanged, which looks like replicated enemy health/shield is not updating even when `Entity3D` state is correct.
- shared 3D debug/performance overlays must not be forced through `PlayerHUDManager3D` when the data is scene-level rather than player-owned. The FPS/ping canvas is a good example: if it is authored like a player HUD target, it inherits unnecessary binding dependencies and can stay blank in scenes where no player has been resolved yet. Keep diagnostic overlays as standalone canvas-owned scripts unless the displayed value actually comes from local-player state.
- shared 3D performance ping labels must not stay on placeholder text once the scene is networked. The earlier `PerformanceStatsHUD3D` always rendered `"-- ms"`, which looked stable but hid real transport latency during live network tests and tuning. Read ping from NGO's active UTP transport RTT and keep the display contract explicit (`RTT * 0.5` one-way estimate) so 3D HUD values match the existing networked duel HUD semantics.
- local-player 3D reticles moved onto the scene HUD must not keep a stale or player-prefab-local aim origin after the component leaves the ship root. The hover hitscan still needs to come from the same camera-centered aim ray the weapons use; otherwise the brackets test one line while the real shots use another. Keep the HUD reticle binding the resolved gameplay camera back into the bound player's weapons so the hover ray and the actual firing path stay aligned.
- local-player 3D weapon select bars must not blindly reuse the reticle's fill semantics for every weapon. If the HUD reuses a resource-usage ratio where the authored ask is remaining availability or ready progress, bars animate backward and mislead the player. Keep the weapon HUD fill calculation explicit about which semantic each slot is using.
- local-player 3D ability select bars must not reuse the legacy `Ability3D.GetHUDFillRatio()` value when the canvas is authored as a ready-progress bar. That older helper reports cooldown remaining, so a copied HUD animates backward unless it reads an explicit cooldown-ready ratio instead. Keep ability HUD fill driven from cooldown-ready progress, and keep the ready flash on the surrounding box rather than on the fill image when that is the authored visual language.
