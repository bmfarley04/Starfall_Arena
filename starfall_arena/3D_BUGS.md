# 3D_BUGS.md

This document is the 3D implementation bug ledger.

Use it for short, actionable notes about regressions, pitfalls, and architectural gotchas that are specific to the 3D translation layer.

Bug note format:

- what failed
- why it matters in the 3D path
- how to avoid repeating it

## Damage And Combat Ownership

- networked 3D combat must not let projectiles, beams, or ability overlap logic apply gameplay damage on every peer. The pre-networked 3D scripts were local-authoritative, so enabling combat input without a broker would make each client simulate its own damage truth. Keep `Projectile3D` / `LaserBeam3D` split into cosmetic-only client instances and server-authoritative gameplay instances through `NetCombat3D`.
- networked 3D player death must not call `Destroy(gameObject)` directly on a spawned player object. NGO despawn is the network-visible operation; direct destroy can leave stale remote player objects, stale tags, and mismatched death presentation. Use server-owned `NetworkObject.Despawn(...)` after broadcasting death effects.
- networked 3D combat impulses must update the movement simulation state, not only the live `Rigidbody`. `NetMovement3D` owns prediction/reconciliation state, so recoil, impact force, tractor pull, and teleport warps can be overwritten on the next tick if they do not also pass through combat velocity/warp helpers.
- networked 3D slow must be treated as server-owned combat state. If the server trusts the owner's submitted slow multiplier, a client can accidentally or intentionally simulate movement with a stale or incorrect debuff state. Server movement simulation should read the server-side `Entity3D` slow value.
- shared 3D victim-hit audio cannot infer beam-vs-projectile behavior after the fact if `Entity3D.TakeDamage(...)` drops the damage source. The earlier contract only passed damage, hit point, and attacker, which meant `Player3D` had no reliable way to decide between shield/hull impact sounds and the looping beam-hit sound. Keep the 3D damage path explicit about source type whenever downstream feedback depends on it.
- shared 3D entities must own shield state and the `ShieldController` reference directly, just like the 2.5D `Entity` path. The earlier `Entity3D` only tracked hull health, so 3D projectiles skipped shield absorption entirely and never triggered the canonical field flicker on hit. Keep shield consumption and shield-hit visual triggering inside `Entity3D.TakeDamage(...)` so every 3D ship reuses the same hook-up pattern.
- shared 3D projectiles must resolve the owning `Entity3D` from the hit collider's rigidbody or parent chain before deciding whether damage should apply. In the 3D scene, shots can hit child colliders such as shield meshes or visual model colliders that are intentionally untagged. If `Projectile3D` only checks the exact hit collider for both tag matching and `Entity3D`, the projectile despawns without ever calling `TakeDamage(...)`.
- shared 3D temporary shield abilities must intercept projectiles from the explicit `Projectile3D` hit path rather than relying on passive trigger callbacks from the shield mesh. A Class2 absorb shield can look visually correct as soon as its shield object is active, but explicit spherecast hits still flow into normal damage unless `Projectile3D.ProcessHit(...)` delegates that impact to the ability first. Keep projectile-impact overrides explicit in the 3D projectile runtime whenever an ability is supposed to absorb, redirect, or otherwise replace the default hit result.
- shared 3D debuff projectiles must extend both `Projectile3D` and `Entity3D` when ported from the 2.5D path. A first-pass Class2 empowered shot port can fire the right projectile prefab and still silently drop its slow effect if the 3D path only ports the ability and not the target-side movement scaling. When a 2.5D projectile carries gameplay state such as slow, burn, or pierce decay, audit both the projectile runtime and the target entity runtime before assuming the ability port is complete.

## Flight, Camera, And Control Feel

- shared 3D movement scripts must not own local-player camera logic. The earlier `Movement3D` mixed universal flight with Cinemachine behavior, which made enemy or future network-driven ships inherit irrelevant camera dependencies. Keep flight reusable and keep camera behavior on player-only components.
- shared 3D flight must not let pitched root rotation leak into a duel-plane movement basis. An earlier `ShipFlight3D` version used the ship's full `transform.forward` for thrust, recoil, and speed evaluation, so rotating the ship off the horizontal plane silently injected world `Y` velocity and looked like gravity was turning on during turns. Keep duel-plane movement projected onto a stable world plane and explicitly zero vertical drift when this path is meant to stay planar.
- shared 3D flight must not keep planar-forward thrust enabled on the active player flight path after the design has moved to real climb/dive. The old `ShipFlight3D` projected thrust and recoil onto a world-horizontal basis and then zeroed `velocity.y`, which made pitch visuals look responsive while actual travel stayed trapped on the old duel plane. If the 3D mode is meant to support real ascent and descent, thrust/recoil must use full forward and the world-Y lock must stay off on the active prefab.
- shared 3D turn feel must not rely on post-physics reactions alone. The earlier combination of direct angular-velocity assignment, reactive-only mesh banking, and a camera that only changed FOV/distance made the ship feel late and disconnected even when the model visibly tilted. Keep steering assist, intent-driven visual tilt, and turn-biased camera framing coordinated as one package.
- local-player 3D anchor states must suppress the effective thrust signal, not just the acceleration application. If Anchor only blocks velocity gain while `ShipFlight3D` still reports raw thrust input as active, thruster VFX and any other thrust-driven presentation keep firing and falsely imply the ship is accelerating.
- local-player 3D KBM free-look must not depend on an unlocked mouse cursor or on stick-style action values alone. In the 3D duel camera path, that caps rotation when the pointer hits the screen edge and can leave the mouse acting like a UI cursor instead of a relative-look device. Keep KBM free-look reading locked mouse delta through `PlayerInput3D`, and only apply that cursor lock while the active control scheme is `key+mouse`.
- local-owner 3D network prefabs must re-assert owner presentation/input wiring when ownership changes or when replicated spawn timing leaves owner input disabled. In the movement-only 3D net path, `ShipFlight3D` runs in external-simulation mode, so if the local owner never re-enables `PlayerInput3D`/`PlayerInput` after spawn, thrust/look stay zero and the ship appears fully unresponsive even though components exist on the prefab. Keep an explicit owner-control recovery hook (`OnGainedOwnership`/`EnsureOwnerLocalControlReady`) and fail loudly when owner movement is running without `PlayerInput3D`.

## Aiming, Projectiles, And Beams

- networked 3D owner combat input must stay suppressed when `NetCombat3D` is missing. The movement-only network phase deliberately blocked combat input because otherwise local projectiles could appear to work while never reaching the server or the other client. Only remove suppression once the prefab has a real combat broker.
- networked 3D owner combat input must re-check the suppression flag after spawn/ownership recovery, not only whether input components are enabled. A client owner can keep moving while `_combatInputSuppressed` remains true, which makes the ship look networked but blocks fire and abilities. Keep `NetMovement3D.EnsureOwnerLocalControlReady()` validating combat suppression against the presence of `NetCombat3D`, and let `NetCombat3D.OnNetworkSpawn()` re-run owner presentation setup once the broker exists.
- networked 3D cosmetic projectile RPCs must fail loudly when a proxy cannot resolve its local weapon/prefab binding. Host fire can work from server-authoritative components while the remote client silently drops the visual RPC if its proxy has no primary weapon fallback or missing projectile prefab reference. Keep `NetCombat3D` resolving primary projectile data from `Entity3D.PrimaryWeapon` first and `GetComponent<ProjectileWeapon3D>()` as a fallback, and keep one-shot warnings around missing cosmetic bindings.
- shared 3D beam docs and implementation must stay aligned on aim source. The beam was documented as center-screen aimed while the runtime still used shooter `transform.forward`, which diverges once the chase camera and ship facing are not identical. Keep beam aim sourced from the same camera-centered path as projectile weapons when an aim camera is available.
- shared 3D projectiles must not trust a tilted visual muzzle's forward vector for player aiming. Once banking/pitching is applied to the visual model, muzzle children can tilt away from the real gameplay aim. Resolve player projectile direction from camera aim or another authoritative target point, then spawn from the muzzle position using that direction.
- shared 3D center-screen projectiles must not rely on muzzle-to-center-point convergence alone once the camera is allowed to lag and frame the ship off-center. That path is mathematically valid but can look like shots are missing the reticle during hard turns because the muzzle starts far from the center ray. Keep a tunable blend back toward the raw center-screen aim direction so off-center chase framing still reads as center aiming.
- shared 3D projectiles must not carry redundant physics components when the hit path is already explicit hitscan/sweep logic. The earlier 3D projectile version kept a projectile collider even though collision results were being decided by scripted casts. That added avoidable component cost and blurred the true ownership of hit detection. Keep the projectile prefab visual-only unless a real gameplay requirement needs its own physics body.
- shared 3D hold abilities such as beam weapons must not inherit tap-ability cooldown gating from `Ability3D.TryUseAbility(...)`. That base path timestamps the press event, which is fine for tap abilities but wrong for hold/release weapons and can look like the beam randomly expires or has a fake regen delay before it can fire again.
- shared 3D beam capacity is an overheat meter, not remaining fuel. If `drainRate <= 0` or `capacity <= 0`, the 3D beam should be treated as non-draining and the HUD/resource gate should stay inactive instead of accumulating invisible heat.
- shared 3D reflect shields cannot rely on `OnTriggerEnter`-style callbacks from the projectile itself when the projectile path is explicit sweep logic. `Projectile3D` decides hits by spherecasting and may not carry a live collision body, so the reflect path has to be checked from `Projectile3D.ProcessHit(...)` before normal damage/despawn logic runs.
- shared 3D reflect shields must not treat reflection as a simple `-direction` flip when the gameplay goal is "send the shot back to who fired it." In full 3D space the attacker can sit above, below, or offset from the incoming path, so a planar reversal can miss even though the parry looked correct. Resolve the reflected heading from the projectile position to the original shooter when that shooter still exists, and only fall back to a raw reverse vector if that ownership context is gone.
- shared 3D charged projectiles must not assume every tier prefab shares the same pivot length. Charge-shot tiers can swap between very short and very long projectile meshes, and some prefabs use a midpoint pivot. If every tier uses the same spawn distance, long shots can spawn back through the ship even though short ones look correct. Keep per-tier forward spawn compensation exposed in the ability config when the projectile art varies by tier.
- shared 3D primary-weapon overheat must not be tracked separately by the weapon gate and the HUD reticle. If `ProjectileWeapon3D` enforces one heat value while `PlayerAimReticle3D` animates a different local approximation, the player gets false feedback about why base fire stopped and future tuning becomes misleading. Keep the overheat state authoritative on `Entity3D`, spend it from the real base-weapon fire path, and have the reticle read that same normalized value for bracket fill.
- shared 3D beam visuals must not use `SphereCast` entry distance as the rendered beam length when the hit effect is placed at `hit.point`. With a forgiving beam radius, `RaycastHit.distance` reports when the cast sphere first touches the target, which makes the visible beam stop short by roughly the cast radius even though damage and impact VFX land correctly. When the beam should visually reach the displayed impact point, derive the rendered length from the hit point projected onto the beam direction instead of the raw cast-entry distance.
- networked 3D beams and tractor beams must not resolve screen-center aim from a local `aimCamera` on any peer except the owning client. `Weapon3D.Awake` caches `Camera.main`, and `NetMovement3D.SetWeaponAimCamera` only rebinds it for the local owner. That leaves the server-authoritative copy on the host and the cosmetic proxy on the opposite client both sampling the viewer's own camera for `ViewportPointToRay`, so the non-host's laser never actually hits the target ship and the remote proxy's visuals point in whatever direction the viewer happens to face. Replicate the owner-computed aim direction on beam/tractor toggle plus per-tick aim-update RPCs and consume that replicated direction on every non-owner peer through `LaserBeam3D.SetNetworkAim(...)` / `TractorBeam3D.ApplyNetworkTractorBeamAim(...)`.
- shared 3D projectile requests that provide a `spawnAnchor` must not silently fall back to the base weapon's full muzzle array when `request.muzzles` is empty. `FireProjectilePattern(...)` fires once per resolved muzzle entry, and `ResolveProjectileSpawnPosition(...)` uses the same `spawnAnchor` each pass, so a single-anchor ability shot can duplicate into 4 stacked projectiles if the base weapon config has 4 muzzles. When a request uses `spawnAnchor` and no explicit muzzle list, resolve exactly one firing source from that anchor.

## Ability Integration

- shared teleport abilities reused from the 2D path must not keep `transform.up` movement, `z` pinning, or `Collider2D`-only disable/restore logic once they are placed on 3D ships. That combination makes the ship blink but still teleport in the old 2D axis basis, leaves 3D colliders active during the warp, and can restore the wrong post-teleport scale if the mesh prefab is authored with non-unit local scale. Resolve teleport travel from the ship's planar 3D forward, preserve the 3D flight-plane axis, and cache/restore both 2D and 3D presentation state.
- shared 3D teleport pulsewave VFX must not keep a fixed world rotation when the gameplay camera follows ship heading. A flat pulse mesh that spawns with a static rotation can look correct from one heading and edge-on or skewed from another. Billboard teleport pulsewaves to the active gameplay camera, and preserve any mesh-authoring axis offset the prefab needs, so departure and arrival reads stay consistent regardless of ship facing.
- shared 3D teleport one-shot audio must not reuse a player-level `AudioSource` that may already be configured for looping beam, shield, or other sustained effects. `SoundEffect.Play(...)` uses the source's current loop state, so a reused looping source makes teleport exit/arrival sounds loop even though the ability only triggers them once. Keep teleport on its own dedicated non-looping `AudioSource` so one-shot playback cannot inherit stale loop settings from another 3D system.
- shared 3D ability hooks must be consumed by the movement and firing drivers, not just exposed on `Ability3D`. Before the charged-shot path was integrated, the 3D runtime defined thrust multipliers, rotation multipliers, and primary-fire locks, but `ShipFlight3D`, `PlayerInput3D`, and the enemy fire loop never read them. That made charge penalties and fire suppression look configured in the ability while doing nothing in play. Keep the runtime querying `Entity3D` for combined ability state whenever a new 3D ability relies on those hooks.
- shared 3D cooldown attacks must not stay wired as `Ability3D` components after the runtime has moved to 3 weapon slots plus 2 ability slots. Leaving cooldown attacks on the ability path makes them invisible to weapon selection, shared fire input, and weapon cooldown HUD state even though they still spawn projectiles. When a combat action is meant to be one of the selectable weapons, port it to `Weapon3D`, put it in the entity weapon array, and mark its availability mode to match its real gating model.
- shared 3D tractor-beam pulls must not reuse planar cone math from the 2.5D path. A planar projection (`ProjectOnPlane`) plus `velocity.y = 0` can make the VFX look active while targets only move on a flat slice and never get true vertical pull. Keep cone-angle tests and pull velocity in full 3D vectors, and treat beam activation/deactivation as explicit state so the visual cannot remain stuck active after timing edge cases.
- shared 3D tractor-beam volume meshes must not default to an opaque or high-alpha end cap when viewed from a chase camera. Closing the cone tip can read like a giant flat screen-space card even when the pull logic is fully 3D. Keep the end cap optional (or very low alpha) so the effect reads as depth volume instead of a billboard.
- shared 3D tractor-beam suction particles must not combine stretch-render mode, trails, and strong noise when the camera sits near the beam axis. That stack can produce intermittent screen-side streak artifacts that look like rendering glitches rather than pull motion. Keep suction particles on deterministic inward velocity (billboard render, no trails/noise outliers) when readability is the priority.
- shared 3D tractor-beam visuals must not be procedurally authored in `TractorBeam3D` when the desired result needs art-directed cone layering and ring spacing. The earlier runtime mesh/material/particle setup technically produced a beam, but it locked the look to code-only parameters and made iteration worse than building the effect directly in the prefab. Keep `TractorBeam3D` responsible for pull logic and activation only, and author the beam cone/rings as a manual child hierarchy referenced through `visualRoot`.
- shared 3D tractor-beam cone aim must not be resolved from a pitched visual spawn transform's `forward` when the gameplay intent is center-screen targeting. The previous `TractorBeam3D` path used `spawnPoint.forward` for cone checks, so a slightly up-tilted ship mesh made the pull volume drift above the reticle and feel detached from projectile/beam aim. Resolve tractor-beam direction from the same center-screen camera ray pattern used by weapons, and keep `spawnPoint` ownership limited to beam origin/visual placement.
- shared 3D tractor-beam visuals must not stay in a static authored rotation once cone aim is camera-driven. A static `visualRoot` can keep pointing upward while pull checks use center-screen direction, which makes the effect look broken even if gameplay is correct. Drive `visualRoot` transform from the resolved gameplay cone direction (with a small configurable rotation offset only for mesh-axis compensation), and use a Scene gizmo to validate cone size/alignment during prefab tuning.

## VFX, Feedback, And Presentation

- shared 3D visual tilt must not derive recoil pitch only from total forward acceleration. In the 3D flight path, weapon recoil is injected as a velocity impulse, so folding it into the same signed acceleration term as thrust can invert the feel and removes independent tuning. Keep thrust pitch and recoil pitch as separate inputs, with recoil sensitivity exposed on `Entity3D`.
- shared 3D death presentation must not stay embedded in `Entity3D` or reuse the 2D ship-part scatter script unchanged. The old path depended on `Rigidbody2D`, planar cone math, and a fake `z` render offset, which reads wrong once the ship is a true 3D object. Keep ship death VFX in `DeathEffects3D`, keep per-fragment behavior in `ShipPartScatter3D`, and scatter with real 3D velocity and angular motion.
- shared 3D one-shot particle effects must not rely on scene unload or manual cleanup to disappear. That leaves invisible-but-alive objects in the scene and defeats pooling. Use `TimedEffectCleanup3D` so temporary VFX either despawn back into `GameObjectPool3D` or destroy themselves after their particle lifetime expires.
- shared 3D split-state lightning must not treat the shader asset itself as if it can place lightning in the world. Stopping at the shader/material step produces no controlled ship effect because nothing defines where the pixels should render. For ship seam lightning, always attach the material to a mesh-bearing `LightningBolt3D` object with explicit anchor transforms, and group those bolts under `SplitStateLightningRig3D` when the whole split-state effect should toggle together.
- shared 3D split-state lightning must not blindly reset bolt visibility in `Awake()` without respecting the renderer's authored enabled state. An earlier `LightningBolt3D` version defaulted its private visibility flag to `false` and then applied that to the `MeshRenderer` on play start, which made bolts look correct in edit mode but disappear the moment the scene began. Cache the renderer's authored enabled state before applying runtime control so preview-visible bolts remain visible unless a rig or gameplay script intentionally hides them.
- shared 3D split-state lightning must not assume every discovered `LightningBolt3D` is fully configured when a rig toggles the effect on startup. An earlier version let `SplitStateLightningRig3D` enable bolts immediately, and any bolt missing a `startPoint` or `endPoint` crashed inside `UpdateQuad()`. Guard bolt activation against missing anchors, log the setup error once, and fail closed by hiding the invalid bolt instead of throwing.
- local-player 3D charge-screen effects must not be implemented as a center-distance vignette when the desired read is energized screen edges. The vignette path biases the effect toward radial darkening/tinting and visibly contaminates the center of the frame. Use a fullscreen edge-glow pass instead.
- local-player 3D fullscreen charge effects must stay owned by one local camera path only. If multiple controllers write the same global edge-glow parameters, whichever updates last wins and the wrong camera can inherit another ship's charge state.
- local-player 3D chromatic-aberration hit feedback must not reuse the 2.5D path's `impactForce`-driven intensity calculation without rechecking the 3D damage contract. The old player script scaled the effect from impact force instead of real damage taken, but the 3D projectile and beam paths call `TakeDamage(...)` without a separate impact-force payload. In the 3D path, drive chromatic intensity from the actual shield/hull damage applied and keep the post-process controller local to the player camera runtime.
- shared 3D speed trails must not be authored from the ship root or from a single center emitter when the look goal is wingtip streaking. That setup turns the effect into a flat center ribbon and breaks the silhouette read from behind. Author explicit wing source transforms and let `ShipSpeedFx3D` build the layered trail renderers from those points so the streaks stay attached to the ship's lateral silhouette.
- shared 3D speed trails must not offset the emitter itself away from the authored wing transform just to fake camera-facing softness or turbulence. World-space emitter drift makes the trail read like it is detached from the hull during flight. Keep the emitter locked to the wing source and let the trail renderer alignment, material, width curve, and gradient sell the softness instead.
- shared 3D split-state piece offsets must be applied as `authored local position + configured offset`, not as an overwrite of the current transform or as repeated incremental pushes. Otherwise the effect either destroys prefab-authored asymmetry or accumulates drift every time the split state toggles.

## HUD And Player-Facing Readability

- local-player 3D HUD managers in network scenes must not keep an explicit scene-player reference with auto-binding disabled. Networked matches spawn runtime player objects, so a scene-authored player reference can leave health/shield text listening to the wrong object while real combat state updates elsewhere. Keep scene HUD managers auto-bound to the local player and retry binding briefly after spawn/ownership setup.
- local-player 3D low-health vignette HUD effects must bind through `PlayerHUDManager3D` instead of ship-prefab-local assumptions. Scene HUD canvases exist outside player prefabs, so ship-local setup can leave the vignette listening to the wrong player or no player in networked spawn order. Keep low-health vignette scripts as `PlayerHUDBindingTarget3D` components with an explicit HUD-manager reference when needed.
- local-player 3D aim-reticle feedback must not raycast from a different origin or camera than the actual weapon aim path. If the HUD closes brackets from `transform.forward` or a different camera while the weapon runtime fires from screen-center camera aim, the reticle can claim "enemy under aim" even though the real shot line disagrees, or stay open while shots are correctly centered. Keep hover/readability checks sourced from the same center-screen aim ray the weapon uses.
- local-player 3D reticle spin must not assume "ability button is being held" means "a shot just happened." Charged abilities can spend most of their lifetime in a held charge state where the player is not actually firing yet, while beam-style abilities really do need continuous spin the whole time they are active. Keep reticle spin sourced from actual weapon fire timestamps or explicit ability spin providers instead of raw input state alone.
- local-player 3D health/shield HUD ports must not move the 2.5D combat-state update logic into a scene manager just because the canvas is different. In the 2.5D path, `Player` owns HUD initialization plus health/shield updates, while the scene manager only supplies the correct canvas binding. Rebuilding the bars from scene-level polling or phase flow makes the HUD easier to desync from real combat state. Keep the 3D HUD as a thin local-player binder that `Player3D` updates directly from combat hooks.
- local-player 3D scene HUD elements must not assume they live on the player prefab or let every spawned player claim the shared HUD in `Awake()`. That breaks as soon as the health canvas, reticle, and spawned weapon/ability HUD live in the scene instead of under the ship, and it becomes outright wrong for future networked ownership where only one player on a peer is local. Keep one `PlayerHUDManager3D` on the HUD, let it resolve the local player, and have each HUD element subscribe to that shared binding.
- shared 3D debug/performance overlays must not be forced through `PlayerHUDManager3D` when the data is scene-level rather than player-owned. The FPS/ping canvas is a good example: if it is authored like a player HUD target, it inherits unnecessary binding dependencies and can stay blank in scenes where no player has been resolved yet. Keep diagnostic overlays as standalone canvas-owned scripts unless the displayed value actually comes from local-player state.
- shared 3D performance ping labels must not stay on placeholder text once the scene is networked. The earlier `PerformanceStatsHUD3D` always rendered `"-- ms"`, which looked stable but hid real transport latency during live network tests and tuning. Read ping from NGO's active UTP transport RTT and keep the display contract explicit (`RTT * 0.5` one-way estimate) so 3D HUD values match the existing networked duel HUD semantics.
- local-player 3D reticles moved onto the scene HUD must not keep a stale or player-prefab-local aim origin after the component leaves the ship root. The hover hitscan still needs to come from the same camera-centered aim ray the weapons use; otherwise the brackets test one line while the real shots use another. Keep the HUD reticle binding the resolved gameplay camera back into the bound player's weapons so the hover ray and the actual firing path stay aligned.
- local-player 3D weapon select bars must not blindly reuse the reticle's fill semantics for every weapon. If the HUD reuses a resource-usage ratio where the authored ask is remaining availability or ready progress, bars animate backward and mislead the player. Keep the weapon HUD fill calculation explicit about which semantic each slot is using.
- local-player 3D ability select bars must not reuse the legacy `Ability3D.GetHUDFillRatio()` value when the canvas is authored as a ready-progress bar. That older helper reports cooldown remaining, so a copied HUD animates backward unless it reads an explicit cooldown-ready ratio instead. Keep ability HUD fill driven from cooldown-ready progress, and keep the ready flash on the surrounding box rather than on the fill image when that is the authored visual language.
